# 设计 → 原型 → 试玩验证

1. 从用户目标与相关设计抽取本次要验证的问题。只澄清会改变实验的关键未知，不因文档未齐拒绝实现，也不从题材自行确定全部玩法。
2. 建立或复用原型里程碑，参考 `templates/milestones/prototype.md`；实现任务参考 `templates/task.md`。明确局部规则、占位边界、输入版本、观察方法与实现依赖。
   新项目在主要玩法实现前保存记录并从管理入口链接，无需写完全部专业文档。引擎选择不作为核心交互确认；明确授权默认方案时记录暂定依据后实施。已有项目使用等价记录。
   需要可见表现时，先明确本轮资产方案或选材委托：占位范围、关键对象与动作资源来源及验证局限。最终美术可待定；“做原型”不能自动解释为接受白模。素材未选时继续不依赖该决定的设计与工程工作，方案方法由美术 Skill 提供。
   能力框架与表现资源分别选择：前者依据规则复杂度、已有工程和维护需求，后者依据本轮动作与可读性；具体选型交给技术/美术参考，不把启用框架或导入动作包记为可玩闭环完成。
3. 检查实际工程、引擎和可恢复基线。新作进入引擎专用实现前须有具体引擎选择或有效选型委托；组合候选、已安装环境或默认玩法授权不能替代它。歧义未解决时继续设计、记录和只读检查，暂停依赖引擎选择的初始化与制作；已有目标工程或明确选择直接沿用。代码助手依据任务在原生工程中实现与集成；执行工具本身不把 GDD 自动转换成游戏。无代码/引擎工具时如实报告停在哪一步。
4. 按实际工程的技术参考和可用工具执行必要的构建/资源检查、启动和相关测试，关联任务、里程碑与输入版本。失败先检查证据，修复后新增执行记录，不覆盖历史。引擎专用命令和测试约定不在此流程中定义。
5. 对照实验计划真实试玩/观察。自动测试只证明覆盖的行为；命令退出码不证明手感、趣味性或美术品质。没有试玩证据保持未验证。
6. 将真实工程入口、运行方法、证据与限制写回任务和里程碑，管理入口链接它们；修订受影响专业文档。依据用户已授权的目标继续修改与复测，阶段取舍不得伪造用户确认。

交付至少包含实际改动、可复现运行步骤和已执行检查。独立导出包与引擎内可运行工程分开记录。验证不支持机制时回到相关设计，不强制从头重做全部文件。

实验需要批量参数或曲线时，按需生成数值表雏形并链接功能规格，不为简单原型强制建表。初始参数标明暂定依据；用户/AI 调参后沿用技术侧的数据交换和验证方法，检查工程实际加载的新值。没有完成加载器或导入映射时仅记录候选表，不称为可调参工程。

共享运行工具可用时将项目命令接入 `game_workflow.py run`，携带 `--task`、`--milestone` 和相关 `--input`。必须直接调用引擎时保留同等输入版本、命令、退出码、日志、产物与状态关联，不能只留宿主临时日志。新项目用 `validate_records.py --layout --production --markdown` 检查交接；已有工程检查等价内容。结构通过不代表玩法或里程碑通过。


结束本轮实施时回写涉及的专业事实、任务/里程碑状态、证据与管理下一步；失败或中断也要保存。新项目按管理文件约定运行 `validate_records.py --layout --production --closeout --markdown` 并处理结果；只涉及局部资产/功能、已有或自定义结构时检查等价记录，不强制补新作里程碑。检查结构通过不代表验收通过。
