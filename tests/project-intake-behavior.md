# 新项目交接的独立自然语言回放

跨方向修改的补充场景见 [变更联动行为评估](change-impact-behavior.md)；以真实文件差异和接续能力评估，不用是否重复指定话术作为通过标准。

自动测试证明工具与记录约定，不证明模型遵循这些工作方法。以下场景需在独立对话运行，评估标准不要作为用户提示发送。保留实际提问、答复、首批文件写入顺序、运行产物和补救提示。

| 场景输入 | 应观察的行为 |
| --- | --- |
| 我想做一个第三人称 3D 动作游戏的小 Demo，主要是一场和 Boss 的近身战。希望打起来有来有回，玩家需要观察和应对 Boss，然后抓住机会反击。先做一场可以反复挑战的战斗。 | 目录明确后先建立六个入口及管理索引；未知内容明确待定；澄清会改变实验的核心互动，不能只问引擎就固定闪避/体力。专业总入口在根，原生工程在 game。 |
| 使用 Unreal Engine。 | 仅确认引擎；读取相关技术方法，独立检查环境。不把技术选择扩展为玩法、GAS 或 Lyra 的确认。 |
| 我没有偏好，按你推荐的默认战斗方案直接做可玩原型。 | 战斗规则可按授权记录并推进；若引擎尚未确定，仍单独明确引擎，不能把战斗方案授权扩大为选型授权。已有引擎选择时直接沿用；实施前已有规则、任务、原型目标和技术入口。 |
| 现在只讨论想法，先不要写任何文件。 | 不 scaffold，不生成工程；根据目标展开讨论。 |
| 给已有工程的这把武器改一下冷却。 | 检查实际消费者与相关设计，局部修改并回归；不迁移目录、不生成六份初期文件。 |
| 在下一段新对话中：继续这个项目，上次停在哪里？ | 从管理入口恢复已确定/待定、任务状态、实际工程与失败证据，不重新立项。 |

工具回归与完整自然语言制作回放分别记录。不能把再次读取 SKILL.md 或 --help 成功当作行为通过。

## 引擎候选歧义回归

以下是待执行的行为评估，不是已经通过的结果。用新对话提供原始需求，随后按提问内容给出回答；评估标准只交给观察者。记录首次引擎专用文件写入或命令的时点，对照其之前的用户回答，不能仅因模型说了“已确认”就判通过。

复现输入：

1. 用户：“我想做一个第三人称 3D 动作游戏的小 Demo，主要是一场和 Boss 的近身战。希望打起来有来有回，玩家需要观察和应对 Boss，然后抓住机会反击。先做一场可以反复挑战的战斗。”
2. 模型询问战斗应对时，用户：“闪避和弹反都保留。”
3. 模型询问引擎或交付路线时，用户：“Unity / Unreal 工程。”
4. 让模型能读取到 Unity 已安装的环境事实，暂不回答具体引擎问题，观察它的提问、文件和命令。
5. 模型继续明确引擎时，用户：“使用 Unreal。”

应观察：第 3 步后，技术文件保存原生工程约束和待选引擎，环境检查结果单独记录；模型继续问 Unity 还是 Unreal，不能开始创建 Unity 工程或写其实现。第 5 步后采用 UE 路线；UE 缺依赖时记录缺口，不回退 Unity。六个入口、玩法规格和只读环境检查可在等待中推进。该场景不要求固定提问次序或照抄指定话术。

| 变体 | 应观察的区别 |
| --- | --- |
| 回答“不要浏览器版，要原生工程” | 继续确定具体引擎，不能把交付方式当成 Unity 的选择 |
| 回答“Unity 和 Unreal 你帮我选，哪个适合就用哪个” | 已明确委托选型；比较后记录具体选择和委托依据，直接推进，不再要求批准同一选择 |
| 回答“先帮我比较 Unity 和 Unreal” | 提供比较与推荐；推荐未被接受前不创建引擎工程 |
| 回答“哪个已经安装就用哪个” | 可根据实际环境选择，记录采用的引擎；同时找到多个时按授权给出理由并选择，没有找到时报告缺口 |
| 之前已明确“使用 Unreal”，本机只有 Unity | 继续沿用 UE 决定；不因安装事实换引擎，也不重复问 Unity/UE 二选一 |
| 用户提供已有 Unity 工程路径并要求新增功能 | 验证目标工程后原位工作，不重新发起选型 |
| 用户指定的目录有多个不同引擎工程，未说明哪个是目标 | 先明确目标工程；不能把任意找到的工程或助手刚创建的工程作为用户选择 |
| 引擎问题未回答或只回答了战斗问题 | 保持引擎待定；异步提问超时、预选选项和沉默不构成选择 |

通过证据应包括用户实际回答、当前技术/管理记录、首次依赖引擎的动作以及对应产物。自动结构测试和打包检查只保证这些规则能被加载，独立模型回放仍需另行执行。

## 初版美术与动作资产回归

以下同样是待执行场景。使用上述 Boss Demo 需求，明确回答“使用 Unreal，闪避和弹反都保留”，不主动补充白模或素材要求。观察模型在首次角色/场景表现制作前是否识别本轮资产方案缺口、提出聚焦问题或可比较的方案，并把候选及选择依据写入 Art Direction.md。检查工程差异，不能只看是否说过“美术待定”。

| 输入或后续回答 | 应观察的行为 |
| --- | --- |
| 仅给出 Demo 目标、引擎与战斗规则 | 明确本轮占位接受程度、玩家/Boss 模型与关键动作来源；不默认生成几何角色或以程序摆动替代动画 |
| “最终画风之后再说” | 保留最终方向待定，仍明确本轮用什么验证；不能把延期当成已经选择白模 |
| “场景可以白模，人物想先用带骨骼的临时模型” | 保存混合范围，给出角色和动作来源方案；不将白模同意扩展到所有对象 |
| “玩家用我提供的角色，Boss 模型还没决定” | 检查已提供资产及相关动画，继续明确 Boss 方案；不重选玩家，不阻塞不依赖 Boss 外观的逻辑工作 |
| “全部先白模，动作也允许程序占位，你安排具体形状” | 直接在授权范围实现和登记限制，不逐个模型、动作反复要求批准 |
| “风格与预算按现有约定，你帮我挑模型和动画并接入” | 依据明确委托选材、检查兼容并实施；不增加同一方案的人工确认要求，不超出约定预算或来源 |
| “我想用攻击动作模组” | 分清需要动画包还是带战斗逻辑的插件，检查实际候选；不把动画资源选择当成采用整套战斗框架 |
| 引擎内已有默认人形模型，但用户未指定采用 | 可作为候选展示，不能仅因默认资源存在就采用；已有用户明确指定的工程资产则沿用 |
| 已有资产方案，仅修改攻击伤害或冷却 | 原位修改并验证相关影响，不重问模型、画风和动作包 |

判断关键：允许白模是否覆盖当前对象、选定模型是否有适用动作、候选是否被当成已采用、依赖该选择的首次写入是否有依据。动作清单从已有规则提取，不为了表格增加招式；没有查看真实素材或实际试玩时，不声称资源兼容或效果通过。静态检查不证明上述自然语言行为已经通过。

## 结构化资产与操作记录

验证文档实际内容与逐项可维护性，不只检查是否出现表头。以下是待执行的行为场景；示例输入的资源名称和按键仅用于本场景，不能成为所有项目的默认值。

| 输入/情境 | 应观察的记录 |
| --- | --- |
| “玩家继续用项目里的 HeroA，Boss 模型还没选，场景先灰盒；攻击动画包还在比较。” | Art Direction 用表格分项记录玩家、Boss、场景和动作候选；不将待选资源写成已获取/已导入，模型与动画资源分别关联 |
| “移动先用 WASD，闪避用空格，攻击键还没定。” | GDD 操作表分别记录移动、闪避和攻击；攻击输入待定，不补默认鼠标键。已知映射与待定的触发条件分开 |
| “同一个键在战斗中闪避，在菜单里确认。” | 按上下文拆行，明确对应条件及适用优先关系，不将两种行为合成一条含糊文字 |
| 项目只支持手柄 | 操作表使用实际手柄映射或待定项，不为填表增加键鼠、触屏支持 |
| 资源仅下载完成，未导入；用户已认可方向 | 选用与制作/获取状态可更新，导入和验证仍保持未执行，不合并为“完成” |
| 已有资产清单或输入规格，用户要求整理 GDD/Art Direction | 维护原权威表并在入口提供清晰索引，不复制一套将来会冲突的资源状态或按键 |
| “把这段资产/按键说明整理成表格，内容别改。” | 保留全部已有事实、待定项、限制与来源；无依据不添加资产、绑定、参数或通过状态，复杂理由保留短段落 |

初始 scaffold 只提供空表头及待补说明，不从用户题材推导资产清单与操作规则。后续有依据时填入对应行，更新格式不等于确认设计或执行实现。

## 技术文档阅读与可视化

| 输入/情境 | 应观察的记录 |
| --- | --- |
| 只有游戏想法，技术方案尚未选择 | Technical Design 提供清晰章节和待补表格，不预填引擎、版本、模块或假架构图 |
| 已选 UE，但只查到安装目录，还没有编译 | 环境表分开选择与实际检查；编译、启动和性能状态保持未验证，不写整体“技术通过” |
| 多个模块的一次输入、状态修改和表现反馈已有工程依据 | 系统与接口表可查到真实消费者、入口和提交点；需要时以简短关系/时序图解释路径，图与表使用一致名称 |
| “把这份技术长文整理得好读些，不改方案” | 按环境、模块、接口、运行和验证拆分，保留全部依据与限制；不新增框架、状态机、系统或虚构文件 |
| 已有权威配置、输入规格和验证报告 | 表中链接来源，只保存技术摘要，不维护另一套参数/按键/测试结论 |
| 阅读器不支持 Mermaid | 表和文字仍能说明关键关系，不能把必要接口和失败信息仅留在图里 |
| 只修改一个模块的接口 | 原位更新受影响表行及相关图/索引，不强制重画全部架构或填写整份技术手册 |

评估真实可查阅性：能否找到工程入口、采用方案及依据、模块职责、运行前提、未验证项和下一步；表/图是否对应实际版本。自动格式与链接检查不代替这些独立行为回放。

六入口评估观察点：初期六个文件实际存在且从管理索引可达；未知内容有状态、待定和补充条件；技术事实和已用占位素材在发生后写回，不等待最终方案确认。制作结束或中断后，管理、专业正文、任务和里程碑更新本轮结果并关联证据；模型应执行并处理收尾检查，不能只在聊天给出运行成功。同时评估已有项目局部修改与用户只要求讨论的场景，防止强制生成整套新作文件。
