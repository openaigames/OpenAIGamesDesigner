# UE 能力选型与动作资源行为评估

这是待执行的自然语言评估场景，不是已通过的行为测试。使用实际安装技能的新任务执行，保留用户输入、提问、决定与产物；不得只检查关键词存在就报告通过。

| 输入与最小上下文 | 观察重点 | 不应发生 |
| --- | --- | --- |
| “先讨论一个近身 Boss 战，不做工程。” | 讨论交互与目标，需要时解释候选，不提前设置框架 | 强制选择 GAS、下载完整示例 |
| “用 UE 做一个按钮打开门的小原型，你决定技术。” | 选择与范围匹配的简单实现，记录委托依据 | 默认建立属性/伤害/联网系统 |
| “UE 游戏有持续叠加状态、多种技能共享资源与冷却，后面可能增很多技能；我不懂框架。” | 主动解释 GAS 与自有实现，区分已确认与可能需求，给理由再处理影响当前路线的决定 | 要求用户先自行研究术语；宣称 GAS 免写所有逻辑 |
| “只做三种能力，但需要可叠加效果和明确的联机预测，技术你决定。” | 比较机制、维护与网络需求，不以能力数量直接排除 GAS；记录实际选择和验证缺口 | “少于十种技能不能用 GAS”；重复要求已委托的批准 |
| 已有工程使用 GAS：“给这个技能增加消耗。” | 检查并修改真实属性/Effect/提交点，复用现有主源 | 重新选框架，建立另一套生命或资源系统 |
| 已有自有战斗组件：“增加一个受击状态。” | 原位检查状态、退出与表现消费者 | 无迁移理由就换 GAS 或新建样例工程 |
| “采用 GAS，只用自制动画，没有动作包。” | 建立实际动画/能力/判定映射与验证 | 声称必须购买第三方动作包才能运行 |
| “我有一个动作模组，希望接 GAS。” | 查明是动画包、控制模块还是完整框架，再核对输入/状态/伤害所有者 | 未检查就同时保留两套伤害结算；把资产导入当完整集成 |
| “GAS 已开启，攻击动画也能播放，可以交切片了吗？” | 检查代表性流程、机制、反馈与品质证据，按缺口推进 | 因插件/动画可用就验收切片 |
| 已有样例派生工程：“继续给这个工程新增功能，保留现有框架。” | 接手真实结构，保护依赖；如用户要求迁移，单独规划范围与证据 | 删除已有框架/历史记录，声称能无损自动迁移 |

同时检查 Technical Design 的选型依据、GDD 的规则、美术入口的资源选择以及任务/验证/管理关联；未涉及的方向不强制重写。源码与安装包应提供一致、可解析的参考入口。
