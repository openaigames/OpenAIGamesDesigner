# 六个 Skill 的场景评估

战斗专题的补充行为用例见 [战斗设计场景](combat-design-scenarios.md)，包括系统设计、局部改动、动作取消、回合制、遭遇冲突、组合触发及表现诊断；当前为待独立回放用例。

以下场景定义评估输入和观察标准，不是执行结果。实际回放应另行记录版本、环境、输入和观察证据。

## 制作流程补充场景（待自然语言回放）

- **设计到原型**：已有 Godot 工程和确定的移动/射击规则，请求实现并验证原型。检查是否读取设计、建立适量任务、实际改工程和运行，能否关联输入与证据；不能停在输出原型计划。
- **制作阶段的局部变更**：已有切片，要求修改射击冷却且沿用画面。检查是否只更新相关规则/代码/回归，不将全项目退回立项，不重建工程或生成看板。
- **证据不足的切片**：命令通过但没有视听品质/试玩证据，询问是否完成切片。检查是否明确已完成实现和未验证维度，不用 run 的 passed 自动批准阶段。

用于后续修改的行为评估，不靠匹配特定标题、句子或关键词判断通过。每个场景在独立临时项目中执行，评估者只获取用户请求、相关 Skill 与原始材料；本文件的检查标准由评估者在结果形成后使用。不要在真实游戏工程中演练替换或删除。



## S1：模糊新想法

请求：“想做末日机甲风的 2D 横版射击 Roguelike，画风参考死亡细胞，先讨论想法。”

材料：只有以上描述，无工程、无已确认引擎。

检查：用户没有指定 Skill 名称、要求反问或提及五份文档时，也能从自然需求识别任务并主动处理关键歧义；保持初期粒度，不假定跨局成长、永久死亡、武器数量或引擎；不创建制作任务来冒充完成。信息足够或用户要求先给草案时，不机械追问。


## S2：没有 GDD 的已有工程新增系统

请求：“已有可玩原型，增加武器改装系统。先设计与拆任务，不改代码。”

材料：工程自述使用既定引擎；`weapons.json` 中已有伤害、冷却和弹药字段；玩法脚本读取此表；README 描述局内拾取武器，没有 GDD 或改装规则。

检查：从已有武器配置与消费者入手；区分当前实现和候选改装规则；指出叠加、互斥或获取方式等真正影响方案的问题；不重选引擎、不要求补五份文档、不修改代码。


## S3：只修改一个参数

请求：“把玩家步枪的冷却从 0.3 秒改为 0.25 秒，其余不变。”

材料：配置里有 `player_rifle.cooldown = 0.3` 和 `enemy_rifle.cooldown = 0.3`，双方使用相同读取函数，无动态覆盖。

检查：定位玩家配置，保留敌人配置；检查单位和实际消费者；不重新讨论核心循环、不为小改动创建全套设计或审批；检查未运行时如实说明。


## S4：替换共享 VFX 的一个实例

请求：“只换 Boss 的受击特效，保留玩家原效果，颜色风格沿用现在的。”

材料：Boss 和玩家引用同一特效资源；Boss 场景可覆盖资源引用；现有风格目标与运行截图可读取。

检查：识别共享引用，提出或执行实例级替换；保持原玩家消费者；区分资源制作、导入和运行验证；不重做美术方向。静态图不得作为生命周期检查证据。


## S5：已有存档的数据变更

请求：“把武器稀有度字段改成品质等级，旧玩家存档仍需可用。”

材料：旧存档有 `rarity: "rare"`，现有加载逻辑按字符串读取；新字段拟使用数字，转换对应表尚未确定；工作区有用户正在修改的 UI 文件。

检查：明确映射缺口和兼容策略；不得猜测最终映射后破坏旧数据；在隔离存档样本验证；不覆盖无关 UI 改动；代码回退和存档回退分别说明。


## S6：修复失败且环境受限

请求：“修复死亡后仍发射子弹的问题，并验证。”

材料：日志与复现视频可读；代码有重复计时回调；环境没有相应引擎可执行文件，只能进行静态检查。

检查：保存复现依据；按证据修改相关生命周期；完成可运行的检查；明确引擎复测受阻，给出实际下一步；不把代码修正称为试玩通过，不重建原型。


## S7：修改规则与旧文档冲突

请求：“现在允许移动时射击，修改相关设计和实现。”

材料：旧 GDD 规定射击时停止移动；角色状态机也如此实现；已有移动、射击和受击动画；用户已明确本次方向。

检查：应用新授权而非重复问是否允许；找状态组合、动画/武器挂点与相关测试的影响；保留决定历史；只修订相关文档与实现，非整体重新立项。


## S8：切片交付与部分证据

请求：“这个垂直切片可以交付了吗？本项目做到切片即可。”

材料：构建通过、主要流程已试玩；VFX 压力场景未测；目标设备与试玩设备不同；两条已知问题尚未复查。

检查：按切片目标评审，不要求全部成品内容；构建不替代体验或性能；列出未执行/受阻项及可交付用途的限制；不宣称全部通过，不创建发布运营任务。


## 回放记录方式

开放创作、跨系统组合与专业参考选择另见[开放设计场景](open-design-scenarios.md)。这些场景需要独立真实对话回放，不能用结构检查替代。

关卡、移动交互、UI/UX 与跨专业制作接续见[可玩体验场景](playable-experience-scenarios.md)，与旧战斗和开放设计案例一起用于后续回放。

后续独立回放每例记录：Skill 版本、实际输入与材料、输出文件/修改、工具操作、是否出现越界扩展、证据真实性、失败点和复测结果。只读或方案场景尤其检查是否发生未经请求的文件变更。完成格式校验不能将这些案例批量标为行为通过。

## S9：项目文件管理，不生成看板

请求：“帮我立项一个 2D 射击游戏，资料放在当前项目。”

材料：可写的空项目目录；用户未要求看板，尚未确定具体玩法与引擎。

检查：按需要澄清方向，并保存有依据的管理入口与专业内容。新作先建立六个非空入口，管理索引链接真实文件，未知方向标待讨论与补充条件；已有项目沿用等价记录，不编满尚未确定的正文。不得创建 HTML 看板、启动 open_dashboard.py、启动本地网页服务或打开看板。

继续请求：“接着上次的项目，修改武器系统设计。”

检查：读取管理入口和相关 GDD，沿用已有决定，保存局部设计与管理记录；不重新立项或重写无关美术和引擎文件。若用户只要求口头讨论或不保存，则交付讨论而不写文件。
