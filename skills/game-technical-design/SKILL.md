# 游戏技术设计

技术变更先落在技术入口或实现规格，再检查对玩法规则、美术资产和验证条件的影响；实现限制导致新的体验取舍时提出候选，不静默改写策划。文档、代码与资产的实际状态分别记录。 跨方向工作按 [变更联动](../game-preproduction/references/dependency-and-change-impact.md) 关联同一变更入口并回写管理摘要；仅安装本 Skill 时沿用项目现有变更记录，缺少管理 Skill 不阻塞本专业工作。

新作 Technical Design.md 入口预先建立。环境检查或实施后主动记录实际版本、架构、工程与运行入口、依赖和限制；这些事实不等待用户确认。GAS/Lyra 等未选择的方案保持待定或记录实际未采用，不能将“选 UE”解释为已选具体框架。交付前回写到文件及管理入口。

技术文档采用分层结构：开头提供简短现状与导航，工程/环境、系统职责、接口、运行入口和验证结果用适用的表格逐项记录；取舍与限制用短段落。模块依赖、状态变化或关键数据流确实需要图示时，使用能在 Markdown 中查看的简短 Mermaid 图，并标明方案或实际实现。格式与证据规则见 [结构化技术记录](references/outputs.md#结构化技术记录)。已有权威配置或规格通过链接引用，不另造一套版本、参数和状态；只涉及小改动时维护对应条目，不强制填写完整技术手册。

参数、配置或字段变化使用 [数据配置与版本](references/data-configuration.md)，追踪生效来源、单位、覆盖、校验和迁移；资产接入、替换或批次制作使用 [资源管线](references/resource-pipeline.md)，明确源文件、导入设置、标识、消费者与恢复。专业方法不等于工具已支持任意引擎操作。

落实关卡、移动、交互和 UI 时，按需使用 [玩法接口与状态落实](references/gameplay-interface-contracts.md)，追踪真实输入、状态所有者、提交点、表现消费者和清理路径；不从通用参考推定项目已采用某个框架。

原型或切片实际制作使用 [原生工程实施](references/engine-execution.md)，将技术方案接到现有代码、场景、资产和运行证据。用户已要求实现时继续实施，不把文档交付当作工程完成。

新作初期使用 references/outputs.md。已有工程接入、功能实现或修改、资产集成、数据迁移与技术问题诊断时，读取 [工程变更与实施交接](references/engineering-change.md)，沿用真实工程的引擎、版本、结构和测试方式。根据任务加深，不要求先重写整份技术文档。

先分清新项目选型、已有工程修订与现有作品逆向。读取体验、规则、平台、镜头、现有工程与本轮目标；仅初期说明采用 [技术证据与方案指导](references/outputs.md)，已有工程按变更参考交付。

## 事实与取舍

- 新作不得从类型/风格直接推出引擎。制作路线需要决定时，聚焦问已有工程、指定引擎或熟悉工具，还是需要比较；已回答、暂定或延期的内容不重问。单独写概览不强制先选完工具。
- 具体引擎未定时，不创建其工程、安装其依赖或开始专用实现。“Unity / Unreal”“原生工程”仍是候选范围，须继续明确；“检测到 Unity 已安装”是环境事实，不是选择依据中的用户授权。只在用户已选定、目标已有工程明确，或明确委托引擎选型时进入该引擎路线。检查环境可独立继续，缺少指定引擎时提出处理方案，不自行切换。选择依据和等待期间可做的工作见 [原生工程实施](references/engine-execution.md)。
- 逆向先核查公开技术资料或获授权的工程证据。未知版本、渲染管线、寻路、存档格式等列为缺口，不能问用户希望原作怎么实现。Mod 文档只能支持其暴露的接入边界，不能当作内部全架构。
- 明确分层：已经证实的技术事实、合理推断、建议的等效实现、未验证部分。等效方案可以很具体，但必须说明它是我们提出的方法；原作一个 bug 不能证明内部缺少某种架构。
- 兼容性、版本与能力可能变化时用官方资料或本地证据核实；宿主禁止查询则保留待核实，不伪称已搜索。引擎路径存在、工程启动、构建成功和性能达标分别记录。

## 立项阶段的技术说明

先根据已确认需求整理 Engine、Rendering、Gameplay、AI、Procedural、Backend、Platform 等适用项；示例里的 UE5、Lumen、LLM、PCG 并非默认选项，未需要的模块不添加。引擎等关键未知先询问并记录选择，细节按当前阶段逐步完善。

初期只说明必要能力与待验证关系；详细设计阶段再给出职责边界、输入输出、状态归属、关键流程和失败边界。对涉及物品或持续成长的系统，说明数据如何跨局保存、重复操作与中断如何处理；按实际游戏需要选择，不向无关游戏强加背包或联网系统。

每个重要选择关联玩家体验或制作条件，并说明收益、成本、依赖与替代路径。只比较影响当前决策的选项，不默认联网、服务器或复杂框架。内容配置、运行状态、呈现反馈应能解释彼此关系，模块名列表不足以代替技术设计。

技术验证明确工程/构建、硬件、分辨率、场景负载、采样与指标口径。没有目标预算就先记录待定，不编造“稳定 60 FPS”。资产导入验证按实际文件类型检查比例、坐标、材质、碰撞与动画等适用项。没有执行就只交付计划，不写通过。

将关键技术问题写成「Technical Question → Prototype 验证」，与 Risk & Assumption List 的假设编号对应；不在立项阶段提前展开完整实现。美术尚未决定时可以规划占位资产接口，不强迫先完成 Art Direction。

## 宿主与交付

默认维护 `Technical Design.md` 或已有引擎技术文件，记录真实工程入口、版本、架构、配置/接口、导入与构建方法；未知保留待定。保存后同步已有项目管理入口的文件状态和变更摘要。用户指定宿主时只更新其允许字段，文档计划不能当作已创建的工程或已提交任务。只要求研究或方案时不安装依赖、创建游戏工程或运行长实验。保留旧证据并说明需复核部分，不生成或启动看板。
