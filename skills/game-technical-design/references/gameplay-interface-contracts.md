# 玩法、场景与 UI 的接口落实

用于关卡、移动、交互和 UI 制作中规则到工程的映射，沿用 [工程变更](engineering-change.md)。不指定引擎类名，不默认事件总线、ECS、GAS 或联网；先查实际工程的入口与状态所有者。

## 从一项行为追到消费者

选一个本轮关键行为，追踪输入来源、资格检查、状态修改、事件/返回值、动画/UI/场景消费者和恢复。表中记录实际文件/符号；未找到的标待定位，不能以理想模块名冒充现有工程。

用 [接口与关键数据流表](outputs.md#接口与关键数据流需要交接时) 将来源、消费者、输入、提交点和失败路径分列；顺序关系难以从表理解时再补简短时序或状态图。GDD 的玩家操作表描述玩家怎样操作，本表描述工程如何响应，互相链接而不复制一套绑定和规则。

配置解释允许的行为，运行状态记录当前事实，表现读取事实。明确每个条件或参数的维护位置及覆盖关系；不要让 UI、碰撞触发器和动画各自保存一份“已完成”。

接口按实际需要定义输入、单位/坐标、时点、输出、失败和重入行为。异步操作需要请求与结果的关联；同步本地调用不必引入消息队列。

## 控制权、过程与生命周期

镜头、移动、界面或交互临时接管输入时，定位获取和释放时点。取消、对象销毁、场景退出、失败与重复请求不能遗留锁或旧订阅。优先复用工程已有作用域/状态机制，不强制增加管理器。

一次性副作用例如扣费、门状态变化应有明确提交点。重复完成事件和迟到结果如何忽略或协调，由实际状态约定决定；不能因为停止动画就认定交易回滚。

动画驱动与代码驱动位移、UI 暂存值与生效值、目标提示与实际执行目标需各自对齐。记录哪个组件校验并提交，其他消费者如何更新。

## 场景与数据边界

变动节点、对象或资源标识时追踪实际引用、加载顺序、出生位置、碰撞/导航、交互触发和已有存档中的相关项。预览场景的配置覆盖可能使测试结果不适用于主关卡，应绑定运行入口。

保存边界按项目现有机制处理：一次交互进行中能否保存、恢复后重放哪些事件、旧引用失效怎么办。没有存档时不为接口任务搭建存档系统。

## 实施与检查

先形成一条最小的真实输入到结果路径，再接适用表现和内容；已授权实现时继续修改工程并运行已有测试。文档表格和 mock 只能检查约定，不能证明引擎集成。

选择有价值的边界：正常执行、拒绝、取消、对象失效、重复/迟到事件、切换界面或场景。按真实依赖取舍，不逐项机械创建测试。

交付规则到符号/资源的映射、配置依据、实现改动、实际命令与日志、仍需玩家体验验证的问题。工具不可用准确停留在未运行状态。
