# 工程变更与实施交接

用于已有工程新增系统、修改功能、资产集成、问题修复或架构调整。技术方案任务止于方案；实施请求在授权范围内推进到实际修改与适当检查。

交接按 [结构化技术记录](outputs.md#结构化技术记录) 组织：环境事实、系统职责、实际入口和验证状态分别用表，设计原因用短段落；关键跨模块关系按需补图。沿用已有权威记录，小改动只更新相关条目，不复制另一份技术全案。

## 最小工程检查

定位真实工程根、引擎/版本、相关运行入口、模块、配置来源及已有构建/测试方法；检查本轮涉及的人工修改。无需扫描全部无关代码或迁移目录。引擎和依赖版本来自工程文件或实际工具输出，不从题材猜测。

沿调用和数据流识别本轮入口、状态所有者、事件消费者及持久化边界。记录文件/符号依据和未运行限制。实现与文档不一致时报告具体差异，不自动选择重写代码或文档。

## 改动方案与接口

需要具体数据合同、覆盖或字段迁移时读 [数据配置](data-configuration.md)；涉及源资产、导入标识、派生物和替换时读 [资源管线](resource-pipeline.md)。按本轮实际依赖深化，不一次加载全部专题。

以满足本轮需求的局部方案为起点；只有现结构确实阻碍目标时才提出重构，并说明必要范围。框架或插件存在不意味着应该换用它；大型依赖和引擎迁移应有项目证据及明确需求。

根据实际问题明确：

- 改动模块、入口及消费者，复用哪些既有能力。
- 输入输出、数据结构、状态归属、事件顺序和失败行为。
- 规则状态与动画/VFX/UI 的同步方式，避免两个独立真相。
- 配置校验、资源引用、加载/释放及生命周期，按实际需要设计。
- 性能目标和测量方法；没有目标时记录待确定，不能把预计当实测。

重大或难逆的选择可沿用项目 ADR（架构决定记录），写明问题、候选、选择及后果；局部参数修正不强制写 ADR。与设计、资产规格和任务保持链接，不复制多份配置。

## 兼容、迁移与恢复

检查实际受影响的存档、配置版本、序列化标识、资源引用、外部接口和构建目标。没有存档/联网等能力时不引入它们。适用时明确旧数据读取、缺省值、非法值、迁移失败和重复迁移的处理。

将代码回退与数据回退分开：代码能恢复不证明已迁移存档或重导入资源可恢复。涉及持久数据变换时保存合适的样本/备份并在隔离副本验证，报告实际恢复路径。不得用版本控制清理或重置覆盖无关人工工作。

## 实施与证据

任务顺序由真实依赖决定，可分别交付配置、接口、运行逻辑、资产接入与检查。每项说明目标产物和可观察完成条件，不把“编写某模块”当作验收标准。

采用现有构建工具和测试约定，选择足以覆盖改动的检查。源代码修改、静态检查、构建、启动、实际玩家流程与性能验证分别报告。环境阻塞记录原因、已完成部分和下一项命令/动作，不声称 Skill 本身能控制尚未接入的引擎。

缺陷修复先保存可复现条件或证据；修复后复查问题与直接关联路径。若无法复现，给出当前证据和下一步诊断，不将推测修复记为已验证。验证失败先定位原因，避免无依据更换架构或无限重试。

交接包含相关文件/版本、设计和资产依赖、执行过的命令与结果、剩余风险以及需要继续的验证。已有用户修改被保留的事实来自检查，不凭空保证。
