# 游戏项目管理

结束一次制作工作前，回写技术事实、美术占位、验证结果、任务/里程碑及管理状态；即使中断也保存接续信息。新作执行 `--layout --production --closeout --markdown` 检查并阅读结果，失败时修复或明确报告未完成。不能把创建六份入口或工具可调用当作管理流程已完成。

新项目默认在根目录建立六个非空入口：管理、概览、GDD、美术、技术、风险验证。正文按已知内容逐步完善，未知用“状态、已知、待定、后续补充条件”记录，不填成既定设计；目录、时机与已有工程例外见 [项目文件与管理入口](references/project-files.md)。目录明确且允许保存时，环境探查可以并行，但不要等主要实现写完才建立记录。新建原生工程默认放在 `game/`；宿主的 `outputs/`、`work/` 不代替游戏项目结构。

进入实现前区分用户明确目标、尚未确定的核心交互与低影响实施默认值。引擎选择不同时确定应对方式、资源机制或招式组合。只澄清会改变当前实验的关键未知；用户明确授权“按你推荐直接做默认原型”时可采用并记录可撤回假设，无需重复确认。

新作进入引擎相关创建或实现前，须有明确的具体引擎选择，或用户确实委托了引擎选型。“Unity / Unreal 工程”只确定原生工程方向，仍需追问 Unity 还是 Unreal；本机安装情况不代替用户选择。等待回答时可整理六份入口、设计与环境事实，不创建候选引擎工程、不编写其专用实现。已有目标工程或此前明确选择直接沿用；授权采用默认战斗方案不自动包含更换或选择引擎。

初版可见表现开始制作前，按美术 Skill 的资产方案方法明确占位/现成素材的范围、主要角色模型与关键动作来源，或记录用户的选材委托。只选引擎或要求 Demo 不等于认可白模；最终风格待定也不等于本轮素材可随意决定。只暂停依赖待选资产的工作，设计与独立工程任务继续；已有明确方案和授权不重复确认。

首次立项建立六个入口，后续从任一专业原位修订。跨方向修改或接续时读取 [依赖与变更影响](references/dependency-and-change-impact.md)：以同一变更入口关联受影响文件、任务与证据，分别追踪设计、实现和验证；在授权范围内完成可确定的关联修改，待决项明确留存。管理汇总每轮变更、阻塞与下一步，概览只在定位或核心体验等承诺改变时更新；局部功能变化不重置全项目阶段。

负责本轮目标、项目阶段、交付范围、依赖和完成依据。五个专业 skill 分别维护其专业内容；总管理不复制专业正文。新作初期读取 [初期结构与协调交付](references/outputs.md)；接手工程、新增或修改功能/系统/资产、准备实现或评审里程碑时，读取 [项目演进与制作交接](references/project-evolution.md)。名称保留 game-preproduction 以兼容已有调用，职责覆盖持续开发。

默认交付可持续编辑的本地 Markdown 文件。建立或接续项目管理时读取 [项目文件与管理入口](references/project-files.md)，维护 `Project Management.md` 或已有同等文件，链接项目概览、GDD、美术、引擎技术和风险验证资料。专业正文保存在各自文件，管理文件保存状态与关联。

数值批量配置、公式推算或用户希望亲自调参时，按需由策划生成表格附件、技术接入现有工程，沿用当前阶段和变更记录。管理入口链接数值主源、导入差异与验证，分别汇总草案、文件写入、运行生效和体验验证，不默认每次立项都生成一套数值表。方法从 game-design 的数值表参考进入。

进入原型构建、垂直切片、功能实现或交付时读取 [制作流程与执行入口](references/production-workflows.md)，使用适用的里程碑、任务和证据流程。已授权实现时接续真实工程工作，不停在策划文档；执行工具记录结果，模型依据证据维护文件，阶段取舍与命令通过分开。

不因新建项目、保存草稿或继续讨论生成 HTML 看板、启动本地网页服务或打开看板。旧看板已从默认技能包移出；只有用户明确要求时才定位源码归档或其指定工具，不假定安装目录含看板资源。正常项目管理无需浏览器界面。

## 先确定任务与深度

用户只需表达目标与约束，不需要输入“先反问”“生成五份文档”或点名专业分工。主动依据需求与现有上下文判断下一步：缺少会改变当前方向的信息时，简短说明原因并提出关键问题；信息足够时直接推进对应工作，将已有依据逐步整理到相关文档。自动处理的是工作方法，不是替用户决定玩法、批准候选或扩大发布/制作范围。用户明确要求先给草案、只讨论或直接修改时沿用其要求，不强制先提问。

依据用户当下目的区分：新作构思、已有工程接手、新增内容、修改/替换/移除、问题诊断、参考研究、验证计划或实施。根据请求和项目证据识别，不额外要求用户选模式；已有项目不重新走完整立项。

新想法采用初期立项深度；已有项目采用解决本轮问题所需的粒度。新增系统可展开详细规则和接口，替换一张贴图通常只需资产与导入检查。沿用现有文档、引擎、配置和任务体系，不为套模板要求补齐五份文档、重选引擎或重建工程。分析、方案、制作准备和实际修改按用户请求区分；已授权的工作直接推进，不因流程增加重复确认。

“以鸭科夫为例写初期文档”是从参考中提炼候选设计，不是复原原团队历史，也不是抄写成品全部功能。“这个结构可以”只认可结构；“这份概览没问题”只适用于当前概览，不能自动确认其他文档、选型或原型。专业模板是默认章节结构，不是强制填满的问卷；示例的题材、机制、四条支柱与引擎均不作为通用预设。

## 每轮选择一个推进目标

1. 读取当前需求、已确认选择、未决事项和相关正文；仅用一两句复述有变化的已知内容，不重复整份项目介绍。
2. 找会改变当前文档或下一步动作的关键歧义。优先处理互相冲突的要求，再处理会影响核心体验、制作成本或已有工程的选择。能晚些决定的细节保留待定。
3. 通常问一个高价值问题，必要时最多三个；每题只解决一个决策，说明为什么现在需要它，并提供少量有区别的选项及取舍。询问具体引擎时，Unity、Unreal、Godot 分别作为独立选项；若先问“浏览器试玩 / 原生引擎工程”等交付方向，回答后仍要解析尚未确定的引擎，不把类别当成具体选择。允许自由回答、推荐或暂缓，不把引擎、平台、预算、团队绑成一题。
4. 若用户不知道怎么选，结合已知条件给一项可撤回的推荐和理由，请其判断；不重复同一问卷。信息足够时直接写需要的内容，不为凑流程继续提问。
5. 根据明确回答整理简短确认摘要，更新有依据的章节；未被回答的问题继续保留。收尾只给一个最有价值的下一步，用户要求逐份看时先交当前一份，不自动推进到整包确认。

当用户只给参考作品名时，先澄清想借鉴的体验，不能默认照搬其死亡、随机、成长或联网规则。资产与引擎在涉及制作路线时聚焦讨论；单写概览不要求所有生产条件先确定。

## 决定、暂缓和确认

- 模型建议标为候选；用户明确选定某一项，才记为该项选择。对清楚回答不再追问同一次确认。
- “先这样”按上下文记为暂定，并保留适用范围；“帮我推荐”不是接受推荐；“还没想好”仍是未决。“暂时看着没问题”仅认可本轮展示的范围，不能升级为永久基线。
- 延期记录被推迟的事项、影响与恢复讨论的条件，例如“确定镜头后再选角色比例”；未指定日期时不编日期，不在条件未变时重复追问。
- 仅当不回答会让当前目标无法继续或迫使模型擅定关键方向时，才视为当前阻塞。美术、最终资产、完整技术方案并非统一的立项门槛；说明能先做的部分。
- 局部选择、文档审阅、立项基线、实验通过分别记录。宿主有独立确认按钮时，模型不能用对话伪造按钮结果；用户的文字选择仍可作为需求依据保存。

## 跨文档协调

一次变更先识别“变了什么 → 哪些已写结论依赖它 → 哪些要改或复核”。沿用同一决定与假设编号，不在五份正文各存一份互相矛盾的结论。

| 变化 | 优先检查 |
| --- | --- |
| 核心体验或 Game Pillars | Concept 的承诺、GDD 的循环与规则，以及受影响的风险假设 |
| 单人改多人、2D 改 3D、平台变化 | GDD 的交互、Art 的表现、Technical 的能力与 Risk 的成本假设 |
| 资产渠道或视觉方向 | Concept 的资产来源、Art 的候选、Technical 的导入与验证依赖 |
| 损失或成长规则 | GDD 的循环、Technical 的状态与持久化、Risk 的体验假设 |

上表是检查入口，不表示每次必须重写全部文档。已有正文若直接冲突，给出具体修改建议；只有潜在影响时标为待复核。无影响的章节保持原样。受 sectionKey/documentId 限制时只修改允许范围，在摘要列出其他待复核处，不越界输出。

## 六个 skill 的分工

| 职责 | Skill | 产出 |

| 项目管理 | game-preproduction | Project Management.md：项目状态、专业文件索引、决定、待决、任务与下一步 |
| 项目概览 | game-concept | Game Concept.md |

按本轮目标使用相关专业方法，不因有六个 skill 就启动六个 Agent。新作六个入口先建立，概览与专业正文随讨论逐步完善；已有项目从相关功能、资产、代码或证据切入。小改动可由单个专业直接完成，不强制经过总管理。已有项目沿用等价文件，不为凑齐文件重做立项。

## 宿主与证据边界

立项范围通常包含管理记录、概览、设计文档、参考材料、待决问题和候选验证。用户当前只推进立项时，资产生产、引擎接入和原型启动作为后续能力，不因文件列有任务就宣称已执行。已有素材可以作为有明确用途和来源的参考关联，不自动升级为正式资产。

默认读取并修订真实文件，保存后返回实际路径。文档内的计划任务可以维护，但不能当作已提交的引擎或生成任务。用户指定宿主 schema 时遵守允许字段和状态机制；已有任务系统优先链接，不另维护冲突副本。没有文件写入能力时交付正文并标明未保存。

区分用户原话、候选、公开事实、观察、推断与验证结果。成品研究依证据，未知历史事实记取证缺口，不请用户替原团队选择。初期回推明确其为设计练习，不冒充真实历史。只有实际查看或执行过才声称看图、联网、运行或通过；宿主禁用工具时说明材料缺口。修改时保留旧决定与证据的历史。
