# 项目文件与管理入口

默认用 Markdown 管理真实项目，不生成看板、不启动网页服务。对话用于讨论和决策，文件用于保存当前项目状态和专业内容。

## 文件位置与职责

新游戏采用下面的默认结构。游戏根目录可以是宿主工作目录内选定的一个子目录，不是工具包或 Skill 安装目录。宿主若提供 `outputs/`，可以把整个游戏项目放在其下，但不要将设计、日志和工程分散在无关联的宿主目录里。

```text
游戏项目/
├─ Project Management.md
├─ Game Concept.md
├─ Game Design Document.md
├─ Art Direction.md
├─ Technical Design.md
├─ Risk & Assumption List.md
├─ design/          详细功能与资产规格
├─ production/      里程碑、任务、决定
├─ assets-source/   源资产或外部资产引用
├─ game/            原生引擎工程
├─ runs/            输入快照、执行记录和日志
└─ builds/          实际构建产物
```

新作初期建立六个非空 Markdown 入口并从管理索引链接五个专业文件；专业内容尚未知时保留状态、已知、待定和补充条件。入口建立不代表设计完成或用户确认；子目录随实际产物产生，不生成空目录或假链接。测试报告可用 `tests/reports/`，资产规格用 `design/assets/`，工具配置用 `.openaigame/`。已有项目结构或用户明确指定位置优先，不自动迁移；刚由模型创建的其他布局不能当成用户已有约定。

先确定当前游戏项目与已有资料位置。沿用现有文档目录、文件名和任务体系，不因下面的默认命名搬动工程或重复创建设计文档。新项目无约定时使用项目根目录下的这些文件：

| 默认文件 | 维护者 | 内容 |
| --- | --- | --- |
| Project Management.md | 项目管理 | 当前阶段与目标、专业文件索引、决定和待决、任务依赖、变更与下一步 |
| Game Concept.md | 项目概览 | 项目身份、玩家体验、设计支柱、定位与来源 |
| Game Design Document.md | 策划 | 核心循环、系统关系、玩法规则、内容与详细功能规格链接 |
| Art Direction.md | 美术 | 风格与参考、角色/场景/UI/动画/VFX/声音要求、资产交付链接 |
| Technical Design.md | 技术 | 引擎与实际版本、工程入口、架构、接口/配置、导入与构建方法；未知选型留待定 |
| Risk & Assumption List.md | 验证 | 假设、风险、实验/回归计划、实际结果与证据 |

引擎侧文件是可维护的技术设计与工程说明，不因创建它就新建引擎工程、安装插件或声称可运行。详细功能和资产规格按需要拆分，索引链接到实际文件即可。

## 建立与接续

用户提出新项目且允许保存工作时，在已知项目目录建立六个入口，概览先保存用户目标，其他专业入口按已有信息填写或标为待讨论；逐步深化本轮涉及的正文。若用户仅希望口头讨论或先不要写文件，遵守该范围。

可用共享工具 `game_workflow.py scaffold --project <项目根> --brief <用户原话>`，不需要先选引擎。工具保存用户输入、六个入口及其真实索引，模型仍需提炼目标、记录关键待决和真实链接；记录已存在时原位接续。开始主要玩法实现前，管理入口应已链接当前设计、原型里程碑和实现任务；探查 API 或创建空工程不等于已选定玩法。

用户尚未命名时可以用明确标注的工作名，不让命名阻塞讨论；不能因此生成额外世界观。项目位置不明确且无法从上下文确定时只询问位置，不把资料写入 Skill 安装目录或随意放入另一个游戏工程。

不为目录完整而一次填满六份正文。新作的六个入口都实际存在，待讨论是内容状态，不是缺少文件。已用的占位资产来源、引擎版本、工程入口及运行结果属于事实，发生后主动填写，不能等待最终美术或技术选型确认才记录。写文档并不表示用户批准了其中候选。

接手已有项目时先读取既有管理/设计记录，使用等价文件。单个修复或资产替换不强制新建完整管理体系；需要持续跨轮协调且没有入口时才创建管理文件。

## 管理文件的最小结构

以下章节按实际内容维护，短表或简短段落均可；不要求固定数量的决定、任务或风险。

1. **项目状态**：工作名、目前目标与阶段、本轮范围、实际更新日期。项目阶段与单个功能状态分开。
2. **专业文件索引**：方向、实际文件链接、当前状态、待复核点。新作五个专业入口都链接；已有项目缺少且本轮不涉及的方向可记待建立。状态可用待讨论、草案、当前范围已审阅、修改后待复核，不用填写率代替成熟度。
3. **决定与待决**：决定编号、具体内容、候选/暂定/已选择/已替代、用户依据、影响文件；未决项记录影响与恢复讨论条件。明确回答直接记录，不再重复确认。
4. **任务与依赖**：任务编号、交付目标、所需输入、依赖、状态、产出/验收依据。初期任务可以是澄清或设计工作，不强制变成代码制作任务。真实执行结果回来后再改状态。
5. **变更与接续**：本轮改动、受影响文件、待复核项、证据位置和下一项可执行动作。保留重要决定的历史，不复制全部聊天记录。

已有 issue/任务系统或专门决定记录时，管理文件维护摘要和入口，不保存第二份会互相冲突的状态。详细规则、美术要求和接口各有自己的正文来源。

## 每轮保存与交接

新项目保存后用 `validate_records.py --project <项目根> --layout --markdown` 检查默认结构和链接；进入原型实现时增加 `--production` 检查最小设计、技术、任务和里程碑入口。已有/自定义结构省略 `--layout`，核对等价内容。工具不判断用户是否确认或规则是否合理，零条运行记录不能证明工程已验证。

开始时读取相关文件与管理入口中的有效决定。只加载本轮需要的专业资料，不要求每次阅读全部文档。

完成讨论或修改后：先保存实际受影响的专业内容，再更新管理入口中的相应链接、决定、状态和下一步。写入前核对文件最新内容并保留人工修改；多文件更新部分失败时明确哪些已保存、哪些仍待同步，不假装整轮已完成。

独立专业任务有现成管理入口时同步相关索引和变更摘要即可，不修改无关任务。没有管理入口且本轮不需要项目协调时，直接交付专业文件。

最后给出实际修改文件的链接，以及一个最有价值的下一步。新对话可以从管理入口恢复进度，无需用户重述完整历史；管理文件不是已执行、可恢复或验收通过的自动证明。


## 实施后的记录回写

交付回复前同步已发生的事实：技术记录实际引擎、架构、工程与运行入口；美术记录已用占位素材、来源及限制；验证记录实际结果、未验证项与中断原因；任务/里程碑更新本轮状态和证据；管理入口更新阶段、目标、工程入口、索引和下一步。阶段可以未完成，不能仍保留“尚未建立”而实际已有工程/里程碑。未来选型待用户决定，已发生事实不等待批准。

新作实施结束（包括失败或被中断）后运行 `validate_records.py --project <项目根> --layout --production --closeout --markdown`；检查报告必须读取并处理，结构不合格不能称项目管理已完成。未能修复时如实保留失败项与下一步，不为了通过修改状态成成功。已有/自定义项目不强套目录，人工核对同等内容。

收尾检查验证六个入口、真实索引、初始占位状态是否残留及证据关联。管理、风险验证、本次任务和里程碑应链接 `runs/<id>/manifest.json` 或 `tests/reports/<id>.md`。直接引擎调用的报告应记录输入版本、命令、退出码、日志/产物路径和观察边界。工具只查结构与引用，不能证明文档事实已完整或模型确实遵循了交互。
