# 项目看板与美术清单

用户要求打开资产看板、浏览本地游戏资产、配置当前项目的生成服务、查看制作确认时使用。界面和程序由工具包共享，每次启动绑定一个真实游戏根目录，不为项目复制网页，也不因为目录存在就自动启动。

定位本 Skill 的 `runtime/`；开发时定位包含 `tools/`、`skills/` 的工具包根。确认脚本存在后运行：

```sh
python tools/project_workbench.py --project "游戏项目绝对路径"
python tools/project_workbench.py --project "游戏项目绝对路径" --view tasks
python tools/project_workbench.py --project "游戏项目绝对路径" --view services
python tools/project_workbench.py --project "游戏项目绝对路径" --approve-job A实际任务编号
```

宿主打开页面时加 `--no-open --ready-file <新临时文件>`，读取返回的本机地址并打开。端口默认自动分配；只监听 `127.0.0.1`。项目看板网址不含一次性凭据，同一台电脑的不同浏览器可直接打开或复制该地址，页面自动建立各自连接；服务需保持运行，重启后端口可能改变。服务校验 Host、Origin、请求头和写入 CSRF，不向其他网站开放跨域接口。Windows 后台启动隐藏窗口，服务需要当前用户的本机配置目录权限；无需管理员权限。不要把密钥或授权记录移到项目中规避权限。已有服务且项目相符时复用，不因换浏览器重复启动；连接过期先刷新，服务退出再启动。独立 `settings_server.py` 的一次性启动机制保持原样。

## 预览格式与边界

GLB/glTF、FBX 与 OBJ 可直接进行 3D 预览。GLB/glTF、FBX 内含动画时支持片段播放/切换、暂停、变速、时间轴和骨骼显示；OBJ 读取其引用的项目内 MTL/贴图，无材质时显示中性几何。FBX 不需要先转 GLB；缺失贴图会提示并使用缺省材质。仅含骨架/动作的 FBX 先显示骨骼，可在“角色预览”选择带蒙皮的同骨架 FBX；名称/层级不一致会拒绝，工具不代替外部重定向。该选择只作用于当前浏览会话，不改变源文件或游戏绑定。动作索引来自浏览器实际解析，未加载前不猜测片段数。预览自动适配显示比例，不作为源单位、根运动或引擎品质验收。常见图片、音频和视频通过浏览器显示或播放，解码支持因格式和浏览器而异。`.vfx.json` 是看板的粒子配置格式，不是 Niagara、Unity VFX Graph 或 Effekseer 原生效果。

UE 等引擎原资源可以直接关联原始项目文件并进入测试，不要求全量导出。需要浏览器内 3D 预览时，再按需导出 GLB 或 FBX，通过 `.asset-browser/previews.json` 关联原文件；助手按具体工程准备导出，扫描器不会自动转换。原资源卡片保留源路径、格式和 Art Direction 标签，副本也登记到同一对象。映射包含源文件、预览副本、实际依赖的 SHA-256；任一登记输入变化时拒绝旧预览。格式与示例见 runtime 中 `tools/README.md` 的“项目看板与资产核查”。导出是否包含动画、材质和场景实例变换，应按产物核实；没有导出的独立引擎动作仍列为引擎资源。

## 资产库与使用范围

共享工作台提供资产库、生成服务和生成任务三个页面。资产库（`--view assets` / `#assets`）提供“候补素材”和“游戏应用”范围筛选。支持格式的本地文件刷新后自动出现，归属依据 `.openaigame/project.json` 的工程及内容根：UE 使用工程/插件 Content，Unity 使用 Assets，其他路线使用引擎根；显式 content_roots 和 asset_exclude_roots 可调整范围。没有配置时才按项目根的 `game/` 判断。配置示例和扫描过滤规则见共享 runtime 的 `tools/workbench/README.md`“游戏内容根”。浏览无需前置登记或阶段晋升。点击卡片直接预览，可按用途分类、文件类型、标签和名称筛选。侧栏“素材方案”展示组合能力、目标覆盖、缺口、取舍与来源，尚未下载的方案也可查看。

游戏应用按目录归属显示，不等于已经运行验证。选择已绑定模型后，详情中可切换“展示动画”；多个角色共用模型时可选择角色，不要求用户先找动作文件再选人物。绑定依据必须来自工程真实配置、资源或引用读回，不能由同目录、相似名称或同骨架推测。未有关联的文件仍正常显示，但不冒充角色动作组合。

角色绑定读取项目 `.asset-browser/characters.json`（version 1）。包含 `characters`（id、title、role、model、actions）、`dependencies`（项目内文件路径到 SHA-256）与可选的 evidence / generatedBy；model 和每个 action.path 必须属于配置的游戏内容根，是真实资产并登记版本。动作项包含 label 与 path。支持多个角色共享模型但具有不同动作列表。清单、模型、动作或配置版本失效时停止使用绑定并显示原因，原文件仍可浏览。扫描器不替引擎自动推导或修改绑定。

UE 原资源浏览预览通过 `.asset-browser/previews.json` 关联 GLB 或二进制 FBX。导出副本保留源文件与依赖版本，按源资产归属显示，不把派生副本重新列为候补。游戏角色的模型与动作均应准备对应预览；动作预览包含已绑定的角色网格，切换时保留人物入口和播放控件。工程真实材质、武器附件、根运动、混合及最终效果仍需在引擎核对，浏览器预览不替代运行表现。

旧 `.openaigame/asset-review/registry.json` 与证据原样保留作历史，不再驱动当前看板。兼容接口保留给既有工具读取；不删除历史，不为了进入游戏栏补做登记/测试/晋升。动画管线需要的专业检查仍在原管线执行和记录，但不是看板的强制流转。Art Direction 仍负责标签，源素材获取和引擎绑定由各自实际记录负责。

旧项目与阶段、运行评审和素材看板链接自动转到资产库。五阶段任务通过 `game_workflow.py task` 及项目记录维护；运行观察通过 `observation.py` 和真实媒体／报告核对，数值模型使用 `numeric_workflow.py` 输出的 HTML 报告。底层记录与兼容接口保留；不要再引导用户进入已移除的页面。

## 分类与用途标签

资产库按“资产范围 → 资产分类 → 用途标签”筛选。范围由实际游戏内容根计算；主分类按单个文件保存；用途标签通过对象 ID 在 Art Direction 中共享；文件格式由扫描器读取。每个可浏览资产显示一个主分类标签，无法判断时显示“未分类”。分类不修改文件位置、对象归属、引擎绑定或验收状态。

主分类沿用看板的人物角色、武器装备、道具模型、地图场景、动画资源、特效美术、材质贴图、音乐音效、二维美术与 UI、插件代码、蓝图与玩法模板。音频可细分配乐、音效、配音。带动作的角色模型保留人物主分类，并显示“含动画”；动画筛选也能找到它，总资产按文件去重。浏览器实际解析到仅含动作而无网格的 FBX 时可修正自动建议，人工保存的分类优先。

取得、生成、制作或接入本轮资产后，依据实际文件、有效引擎类型和绑定核对分类；目录仅提供与文件类型兼容的建议。整包的模型、贴图、动画、声音分别归类，不把包名或父目录分类赋给全部依赖。用途标签如“主角、Boss、冰属性”可共享；“人物角色、动画资源”等分类只针对具体文件，不批量写入对象共享标签。旧项目已有同名用途标签先保留，不以标签文字猜测并覆盖历史归属。

分类的唯一保存入口是 `.openaigame/asset-taxonomy.json`，沿用现有 schemaVersion 1，并为新保存条目记录 `sha256`。纯扫描只读，不自动建立登记文档或锁定目录建议；有依据的分类修正可在已授权任务中批量完成，无须逐个资源重复确认。Art Direction 的“类型”仍记录原文件类别，不改成主分类；规格和清单引用同一分类记录，避免维护第二份可编辑分类表。

看板“修改分类 / 批量分类”与共享 runtime 的 CLI 使用同一保存逻辑：

```sh
python tools/asset_audit.py --project "游戏项目绝对路径" --classify weapon --paths "assets/Sword.fbx"
python tools/asset_audit.py --project "游戏项目绝对路径" --classify audio --audio-kind sfx --paths "assets/Hit.wav"
python tools/asset_audit.py --project "游戏项目绝对路径" --reset-classification --paths "assets/Sword.fbx"
```

文件替换后旧分类保留为待核对信息，不继续作为人工分类生效；旧条目缺少文件版本时同样核对后保存。文件移动仅在原路径消失、内容哈希和扩展名相同且新旧各只有一个对应文件时提示原分类；核对并保存后转到新路径。重名、重复副本或多个候选不自动迁移。扫描报告包含待核对与原路径缺失项；移动源文件时仍需分别维护实际对象、预览和引擎绑定记录，分类不能替代这些关系。

已移除的专题不再提供编辑入口；旧专题数据兼容读取，修改分类不顺带清除它。独立安装而缺少共享工具时维护本轮已有规格，说明分类记录尚未同步，不另写不兼容的分类文件。

## 数据由谁负责

- 固定扫描器发现支持格式的文件、读取信息、计算版本并对照记录，提供预览与差异清单。普通目录忽略构建缓存、依赖目录和隐藏配置；已登记的生成任务输出通过实际记录加入。
- Art Direction 保存对象、用途和共享用途标签，以及本地文件与对象的关联。看板从同一入口继承用途标签；资产主分类由上述分类记录维护。
- 模型结合已有方向、稳定 ID、规格和实际资产证据补齐归属。没有依据时保留待补齐；不能根据文件名把所有机器人、音效或特效自动归给主角。

同一对象的模型、动画、2D、音效和 VFX 通过对象 ID 共用标签，文件类型仍独立。看板刷新时重读文档；目前没有后台目录监听，也没有后台模型调用。

## 检查并补齐

```sh
python tools/asset_audit.py --project "游戏项目绝对路径"
python tools/asset_audit.py --project "游戏项目绝对路径" --init-art
python tools/asset_audit.py --project "游戏项目绝对路径" --register-missing
```

第一条只读，返回未登记、对象/标签待补齐、登记文件丢失及内容版本变化。第二条显式建立空记录区：缺少美术入口时建立简短文档；已有文档追加标记区并保留原文。损坏或重复标记不会覆盖。第三条仅补登记已扫描文件的路径、类型、来源和 SHA-256，未知用途、采用/导入/验证状态保留待确认。看板的“检查美术清单”提供同样操作。

第一次接入旧项目，先读原 Art Direction 及其权威清单。记录区是文件映射，不把旧表全部视作不存在；沿用已有资产与对象 ID，将已知对象归属和标签迁入同一个权威入口，其他规格继续链接原记录，避免复制第二套美术资产状态。程序不对任意历史表格作语义迁移。确有项目自定义入口，在 `.openaigame/workbench.json` 设置项目内相对路径，例如 `{"art_document":"design/art.md"}`；无需迁移原文件。

记录区为 Markdown 表格：

- `<!-- art-objects:start -->` 到 `<!-- art-objects:end -->`：`对象 ID | 对象/用途 | 标签`。标签用顿号分隔，最多 20 个，每个 1–24 字。
- `<!-- art-assets:start -->` 到 `<!-- art-assets:end -->`：`资产 ID | 对象 ID | 类型 | 名称 | 文件路径 | SHA-256 | 制作/导入状态 | 来源与许可`。路径相对游戏根，未知对象用 `—`；同一文件只登记一行。表格中的竖线转义为 `&#124;`。

模型可以直接维护这些表，或使用看板的“设置用途 / 修改用途标签”。写回前重读最新文档，保留原有 ID、说明与证据；表外文字保持原样。页面保存带文档版本校验，发生竞争修改时先刷新和合并。文件改名/移动先核对旧身份；哈希变化先核对内容再更新记录，不直接确认新版已采用。程序绘制、系统资源和计划项仍记录在已有美术规格中，不虚构文件满足扫描表。

获得或修改资产后，若本轮需要登记/看板对齐，执行检查并在授权范围内补齐文件事实和有依据的归属，再检查一次。报告残留缺项及原因；登记完成不代表美术质检、引擎导入或游戏内验证完成。只浏览时不自动改文档。

## 服务与生成任务

服务页复用原有 Windows 用户加密存储，不回显密钥、不保存到项目、不调用平台验证。没有项目时原 `settings_server.py` 独立入口继续可用。

生成任务页读取 `.openaigame/asset-jobs` 的真实任务。内置生图保存交给助手的请求；Tripo／混元 3D、ElevenLabs、Seedream 和 Seedance 沿用实际 API 适配。普通栅格生成的默认选择及例外见 game-art-direction 的 [生成工具选择](../../game-art-direction/references/generation-tool-selection.md)。底稿与参考版本会映射成该工具支持的真实输入快照，任务详情展示实际文件。云端新生成仍由用户核对具体任务并完成费用授权；内置任务不会自动切换收费服务。保存请求不会启动生成。

看板确认复用现有一次性授权机制，绑定项目、任务、请求与账户。确认后助手在既有任务授权范围运行 `asset_workflow.py --project <根> run --job <ID> --timeout <秒>`；看板读取任务状态和结果，不自行启动收费请求。有效授权直接复用；失败先检查/恢复已有云任务，不自动重复生成。页面保存密钥、创建任务、用户批准、工具执行、结果登记与游戏验收是分别可核查的步骤。

## 模型动作预览与历史取舍记录

共享看板的模型预览不再附带“动作取舍”表单，不要求填写角色用途、用途 ID、保留或弃用、动作语义、根运动与镜像需求。动作列表、播放暂停、速度、时间轴、骨架显示及工程关联动画继续使用；切换资产或动作不再触发旧取舍表单的未保存提示。

已有 `.asset-browser/motion-review.json` 及备份保留，历史查询、保存和导出接口继续兼容。接口说明见共享 runtime 的 `tools/workbench/motion-review.md`；不要引导用户在模型预览中填写已移除的表单。共享看板不提供动作检查页面；浏览器模型播放不代替引擎验证。

## 资产迭代历史

资产库沿用现有页面，以版本组折叠同一交付物。详情提供历史、图片双版对比、重新选用、归档和从旧版继续修改；特殊格式沿用现有预览能力。当前选用、最新生成与工程中的实际文件分别显示，不新增测试或晋升流程。

项目 `.openaigame/asset-versions/index.json` 保存版本关系、文件摘要与选用记录；实际快照在同目录保存。Art Direction 只保留当前选用入口和专业正文。分类仍针对文件，游戏范围仍由内容根决定。完整登记方法见 [资产版本与迭代记录](../../game-art-direction/references/asset-versions.md)。旧文件不自动猜测历史；API 任务成功后的登记失败可使用 `asset_versions.py link-job` 恢复，不能自动再发生成请求。

## 动作检查方式

共享看板不提供动作检查、片段编辑和原生预览回传界面，也不加载其前端模块。旧 `--view actions` / `#actions` 兼容转到资产库。模型自带动画的播放、切换、变速和骨架显示继续使用。

项目中的动作记录、草案、应用历史及引擎适配器保留，不修改游戏配置。需要实际检查时使用引擎原生工具和 [跨引擎动作记录 CLI](../../../adapters/engines/action_timing/README.md)。[编辑协议](../../../adapters/engines/action_timing/EDITING.md) 与 [原生回传协议](../../../adapters/engines/action_timing/PREVIEW.md) 面向自定义客户端开发，不是看板操作指南。

## 生产过程与登记联动

制作、获取、导入与替换使用 [资产生产登记与交付检查](asset-handoff.md)。扫描保持只读，“未登记”继续提示真实记录缺口；批量发现文件不替代用途、采用和接入记录。共享生产入口自动写文件事实，实施方同步消费者和验证，交付检查核对本轮范围。历史清单采用显式映射、沿用 ID，并可继续使用 art_document 指定的原文档。
