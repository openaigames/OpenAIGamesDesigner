# 项目看板与美术清单

用户要求打开资产看板、浏览本地游戏资产、配置当前项目的生成服务或查看制作确认时使用。界面和程序由工具包共享，每次启动绑定一个真实游戏根目录，不为项目复制网页，也不因为目录存在就自动启动。

定位本 Skill 的 `runtime/`；开发时定位包含 `tools/`、`skills/` 的工具包根。确认脚本存在后运行：

```sh
python tools/project_workbench.py --project "游戏项目绝对路径"
python tools/project_workbench.py --project "游戏项目绝对路径" --view services
python tools/project_workbench.py --project "游戏项目绝对路径" --approve-job A实际任务编号
```

宿主打开页面时加 `--no-open --ready-file <新临时文件>`，读取返回的本机地址并打开。端口默认自动分配；只监听 `127.0.0.1`。项目看板网址不含一次性凭据，同一台电脑的不同浏览器可直接打开或复制该地址，页面自动建立各自连接；服务需保持运行，重启后端口可能改变。服务校验 Host、Origin、请求头和写入 CSRF，不向其他网站开放跨域接口。Windows 后台启动隐藏窗口，服务需要当前用户的本机配置目录权限；无需管理员权限。不要把密钥或授权记录移到项目中规避权限。已有服务且项目相符时复用，不因换浏览器重复启动；连接过期先刷新，服务退出再启动。独立 `settings_server.py` 的一次性启动机制保持原样。

## 预览格式与边界

GLB/glTF 与 OBJ 可直接进行 3D 预览。GLB/glTF 内含动画时支持片段选择和播放；OBJ 读取其引用的项目内 MTL/贴图，无材质时显示中性几何。常见图片、音频和视频通过浏览器显示或播放，解码支持因格式和浏览器而异。`.vfx.json` 是看板的粒子配置格式，不是 Niagara、Unity VFX Graph 或 Effekseer 原生效果。

UE 等引擎原资源需在引擎中导出 GLB，再通过 `.asset-browser/previews.json` 关联原文件；助手按具体工程准备导出，扫描器不会自动转换。原资源卡片保留源路径、格式和 Art Direction 标签，副本也登记到同一对象。映射包含源文件、GLB、实际依赖的 SHA-256；任一登记输入变化时拒绝旧预览。格式与示例见 runtime 中 `tools/README.md` 的“项目看板与资产核查”。导出是否包含动画、材质和场景实例变换，应按产物核实；没有导出的独立引擎动作仍列为引擎资源。

## 数据由谁负责

- 固定扫描器发现支持格式的文件、读取信息、计算版本并对照记录，提供预览与差异清单。普通目录忽略构建缓存、依赖目录和隐藏配置；已登记的生成任务输出通过实际记录加入。
- Art Direction 保存对象、用途和共享标签，以及本地文件与对象的关联。看板仅继承这些标签，不维护补充标签库。
- 模型结合已有方向、稳定 ID、规格和实际资产证据补齐归属。没有依据时保留待补齐；不能根据文件名把所有机器人、音效或特效自动归给主角。

同一对象的模型、动画、2D、音效和 VFX 通过对象 ID 共用标签，文件类型仍独立。看板刷新时重读文档；目前没有后台目录监听，也没有后台模型调用。

## 检查并补齐

```sh
python tools/asset_audit.py --project "游戏项目绝对路径"
python tools/asset_audit.py --project "游戏项目绝对路径" --init-art
python tools/asset_audit.py --project "游戏项目绝对路径" --register-missing
```

第一条只读，返回未登记、对象/标签待补齐、登记文件丢失及内容版本变化。第二条显式建立空记录区：缺少美术入口时建立简短文档；已有文档追加标记区并保留原文。损坏或重复标记不会覆盖。第三条仅补登记已扫描文件的路径、类型、来源和 SHA-256，未知用途、采用/导入/验证状态保留待确认。看板的“检查美术清单”提供同样操作。

第一次接入旧项目，先读原 Art Direction 及其权威清单。记录区是文件映射，不把旧表全部视作不存在；沿用已有资产与对象 ID，将已知对象归属和标签迁入同一个权威入口，其他规格继续链接原记录，避免复制第二套美术资产状态。程序不对任意历史表格作语义迁移。确有项目自定义入口，在 `.openaigame/workbench.json` 设置项目内相对路径，例如 `{"art_document":"design/art.md"}`；无需迁移原文件。

记录区为 Markdown 表格：

- `<!-- art-objects:start -->` 到 `<!-- art-objects:end -->`：`对象 ID | 对象/用途 | 标签`。标签用顿号分隔，最多 20 个，每个 1–24 字。
- `<!-- art-assets:start -->` 到 `<!-- art-assets:end -->`：`资产 ID | 对象 ID | 类型 | 名称 | 文件路径 | SHA-256 | 制作/导入状态 | 来源与许可`。路径相对游戏根，未知对象用 `—`；同一文件只登记一行。表格中的竖线转义为 `&#124;`。

模型可以直接维护这些表，或使用看板的“补齐美术记录 / 修改对象标签”。写回前重读最新文档，保留原有 ID、说明与证据；表外文字保持原样。页面保存带文档版本校验，发生竞争修改时先刷新和合并。文件改名/移动先核对旧身份；哈希变化先核对内容再更新记录，不直接确认新版已采用。程序绘制、系统资源和计划项仍记录在已有美术规格中，不虚构文件满足扫描表。

获得或修改资产后，若本轮需要登记/看板对齐，执行检查并在授权范围内补齐文件事实和有依据的归属，再检查一次。报告残留缺项及原因；登记完成不代表美术质检、引擎导入或游戏内验证完成。只浏览时不自动改文档。

## 服务与制作任务

服务页复用原有 Windows 用户加密存储，不回显密钥、不保存到项目、不调用平台验证。没有项目时原 `settings_server.py` 独立入口继续可用。

制作页读取 `.openaigame/asset-jobs` 的真实任务，可新建 Tripo / 混元 API 文本生成请求；保存只建立队列。其他类型、参考图和高级参数仍由现有 `asset_workflow.py submit` 准备，提交后在看板核对完整参数与输入文件。用户核对服务、请求和费用提示后确认；助手不能代替用户确认实际收费生成。

看板确认复用现有一次性授权机制，绑定项目、任务、请求与账户。确认后助手在既有任务授权范围运行 `asset_workflow.py --project <根> run --job <ID> --timeout <秒>`；看板读取任务状态和结果，不自行启动收费请求。有效授权直接复用；失败先检查/恢复已有云任务，不自动重复生成。页面保存密钥、创建任务、用户批准、工具执行、结果登记与游戏验收是分别可核查的步骤。
