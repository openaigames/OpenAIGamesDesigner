# 项目演进与制作交接

适用于已有项目接手、新增功能/系统/资产、修改/替换/移除、制作准备、问题诊断和里程碑评审。简单改动直接采用相关段落，不要求每次执行完整流程。

持续管理以 `Project Management.md` 或现有同等记录作为入口，具体文件职责与保存规则见 [项目文件与管理入口](project-files.md)。新建或修改专业文件后维护对应索引和状态，不生成看板。

## 从当前工作开始

先识别用户希望得到建议、设计稿、任务拆分、实际修改还是验证结果。用户明确要求实现时，按已授权范围执行；不要把实施请求降级为仅交计划，也不重复请求已给出的授权。

读取相关目录和项目说明、已有决定、当前功能/资产及必要的版本线索。优先找这次变更的入口和消费者，不要求全仓库审计。只有文档时可以完成设计，标明实现状态未核查；只有工程时从代码、配置和实际画面建立最小现状说明，不要求先补完五份设计文档。工程路径确实未知且无法从环境确定时才询问路径，独立的需求分析仍可进行。

区分用户要求的目标、文档描述的设计、当前实现和实际运行结果。冲突时分别记录依据及后果；代码存在不代表功能可用，旧文档也不自动凌驾于用户的新要求。尚不能判断意图的差异不擅自统一。

## 按变更规模交付

| 请求 | 主要工作 | 通常不需要 |
| --- | --- | --- |
| 接手已有项目 | 找到当前入口、阶段证据、未完成工作和本轮目标 | 重建目录、重新选择引擎 |
| 新功能/新系统 | 定义与既有循环的关系，列接口、资产需求和验收 | 重写全部概览、全项目排期 |
| 新增内容/资产 | 检查现有内容结构、命名、规格、引用和导入方式 | 将内容新增扩成新系统 |
| 修改参数/表现 | 检查真实配置来源、消费者和局部效果 | 强制创建设计长文或新实验项目 |
| 替换/移除 | 找消费者、兼容要求、历史数据与恢复方式 | 未经检查清空旧资源 |
| 修复问题 | 保存复现条件，定位责任层，修复并检查关联路径 | 借机重构无关模块 |

文档、资产、代码、存档/配置、测试、构建分别检查实际受影响项。输出具体路径或对象；未知位置写待定位，不制造文件、任务或关联已存在的假象。

## 功能与变更记录

跨专业变更按 [依赖与变更影响](dependency-and-change-impact.md) 关联同一个入口；各专业修订自己的规则与交付，管理汇总，概览只在定位或体验承诺改变时更新。优先更新现有 issue、任务卡、功能规格或项目记录。没有体系且工作需要跨轮跟踪时，可创建一份聚焦的变更记录，位置沿用项目惯例；无惯例时可用 `design/changes/<变更名称>.md`。小改动的提交说明或最终回复足以交接时，不额外建表。

按需要记录以下信息，空项省略，不将模板变成问卷：

- 目标与依据：希望改善哪种玩家体验或制作问题，相关功能/需求编号。
- 现状与目标差异：当前规则/资源/行为及来源，本轮增加、修改或移除什么，哪些是候选。
- 范围与约束：本轮交付及明确不包含的相邻功能，需保持的接口、风格或存档行为。
- 影响与交接：相关规则、资产、接口/配置、任务、测试和文档的现有链接；责任专业与依赖。
- 验收与证据：什么行为或画面支持完成，如何检查，实际版本与结果。
- 待决与恢复：关键未知、可继续部分、恢复方式及其实际可用性。

沿用已有编号；确需新编号时保持稳定。设计摘要链接专业规格，避免每张任务卡复制整份 GDD。单独修改资产不必创建功能编号。

## 制作任务与阶段

任务拆到能够独立交付和检查的粒度。记录目的、输入/依赖、产出位置、完成条件、阻塞及下一步；只有实际有人或工具承担才填写执行者。估算说明依据和不确定性，不凭空填工期或成本。

沿用项目状态。无既有状态时可区分：待澄清、可执行、进行中、待验证、已验证、受阻、取消。状态随真实证据更新；方案写好只表示设计交付完成，不能标记实现完成。用户接受风险可记录为接受风险，不改写失败测试。

项目阶段和单个功能的成熟度分开：制作中的游戏可以新增实验性功能，不因此把全项目退回立项。下面是按目标选择的判断依据，不是每个任务必须经过的审批链：

| 阶段 | 应回答的问题 | 有效依据 |
| --- | --- | --- |
| 方向探索 | 想让玩家获得什么体验？ | 可讨论的方向、支柱和关键未知 |
| 机制实验 | 这个具体机制是否值得保留？ | 可回答假设的实验与观察；设计稿不等于试玩 |
| 制作验证/垂直切片 | 能否在有限范围达到目标品质？ | 代表性内容的玩法、美术、技术集成，真实运行和成本/性能观察 |
| 内容制作 | 如何重复生产并保持一致？ | 可复用规格、交付依赖、集成与回归记录 |
| 交付与维护 | 本次版本可以交给谁、用于什么？ | 对应构建、已验路径、已知限制及反馈入口 |

里程碑说明目的、范围、验收证据和剩余风险。原型、垂直切片或完整游戏可以分别是最终目标，不强迫项目走向发布。新结果足以改变范围时提出具体取舍，已明确的用户决定直接应用。

## 变更传播与接续

沿“目标/规则 → 配置/资产/接口 → 实现 → 验证”检查依赖。只更新确认受影响的项目，潜在影响标待复核；无关内容不重写。策划、资产和技术可并行准备的部分不因非必要未知全部暂停。

开始实际修改前识别已有人工修改和可恢复状态；使用项目已有版本工具或适当备份，不假定已提交、不覆盖未保存工作。若涉及不可恢复操作或范围扩大，先完成可审阅的方案并按实际授权处理；普通授权内编辑不新增审批。

阶段结束或中断时留下：当前版本/文件、已做与未做、下一项可执行动作、阻塞、证据位置。执行失败区分工具问题、数据问题、实现问题与设计假设失败。仅在原因可处理且范围仍合适时重试；没有执行能力则交付具体交接，不声称引擎、生成工具或恢复系统已接通。

用户指定任务系统或宿主字段限制时沿用其接口，必要的文件交付如实链接；不能把文件内计划当作已提交的外部执行任务。普通文件工作流无需建立数据库或界面。
