# 初期文档预设与管理交付

本文件仅用于新作初期立项。已有项目接手、新增或修改内容、制作任务和里程碑采用 [项目演进与制作交接](project-evolution.md)，沿用项目现有文档与任务，不要求生成以下五份文件。

## 管理入口与专业文件

按 [项目文件与管理入口](project-files.md) 建立管理文件和以下五个专业入口，正文随讨论逐步形成。入口有状态、已知、待定与补充条件，不是空文件。已有模板或用户指定顺序优先。章节可留“待讨论”“候选”或“不适用及原因”，不为了结构完整填入未经选择的设计；入口建立不要求一次完成全部正文。

| 文件 | 默认章节 | 初期应达到的深度 |
| --- | --- | --- |
| Game Concept.md | 项目介绍、Game Pillars、目标玩家、独特体验、世界观与玩家身份、典型游玩体验、影响定位的制作策略（按需） | 新读者能理解项目及希望保护的体验；有待确认处仍可讨论 |
| Game Design Document.md | Core Loop、适用的 Meta Loop、系统关系（文字、表格或按需绘图）、玩法规则与边界、关卡与成长原则 | 解释系统为何存在、如何互相作用；不列完整数值与内容表 |
| Art Direction.md | 视觉与声音方向表、角色场景色彩、UI/特效/声音、参考说明、Moodboard、Concept Art、Reference Image | 少量候选和可补充占位；不要求已有整套资产或完整规范 |
| Technical Design.md | 目标平台、空间与镜头、引擎方向、技术模块、依赖与取舍、关键技术验证 | 能力需求、待决问题与验证方向；不预定完整架构和接口 |
| Risk & Assumption List.md | 假设/风险/Prototype 表、首个实验问题、观察口径、候选验证范围、暂不展开内容、制作条件 | 找到下一步值得验证的判断，不虚构已批准计划或测试结果 |

项目介绍不包含首版范围、不做清单与人员预算工期。风险文档中的首版范围在初期只表达候选验证边界，不等于最终发售承诺。跨文档使用同一假设编号；每份只维护当前结论与必要来源，历史对话不混入正文。

## 本轮交付

根据实际发生的事，简短说明：本轮明确了什么；当前待选问题或建议；哪些文档/章节发生变化；下一步先做什么。没有变化、没有问题的部分省略，不机械输出四个空标题。用户逐份审阅时只呈现当前文档的内容和相关问题。

管理信息写入 `Project Management.md` 或现有同等记录：维护文档索引、当前阶段、决定、待决事项、任务与下一步；专业正文不复制到管理文件。详细风险与实验引用风险文档。只在真实保存后报告文件已更新，不创建看板或用会话回复冒充持久记录。

## 推进判断

用“是否能作下一项决定”判断进展，不用填写率或字数。可以呈现：待讨论、已有草案、当前范围已审阅、变更后待复核；美术等延期项保留具体说明。

进入原型讨论的依据是：有明确要验证的体验、能执行的候选范围与依赖、知道要观察什么。专业文件不必全部详尽。文件存在不等于方向确认，任务写入不等于执行；确认范围和验证证据分别记录。
