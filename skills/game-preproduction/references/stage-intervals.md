# 五阶段区间与任务状态

阶段为立项、玩法验证、制作验证、内容制作、最终交付。按用户目标识别起点、终点、工作对象、已有输入和交付要求，支持 `1 ≤ start ≤ end ≤ 5` 的十五种连续区间。用户无需填写编号；仅在实质范围有歧义时澄清。单个专业小修可沿用现有任务，不强制使用结构化编排。

先素材后方案、先需求后搜索、参考研究、已有工程接手是输入方式，可以与任意适用区间组合。完整策划不必启动引擎；端到端任务要推进到约定内容交付；“编排任务创建成功”不代表已经制作游戏。

## 接手与专业协作

核对本轮所需基线和证据；中段进入不补造前面阶段的通过记录。缺口能在原授权内补齐时继续，根本目标/范围发生变化时提供具体依据再澄清。修复回到原因所在的动作、资产、规则或空间，保留有效工作，随后继续原区间。对象成熟度可不同于项目总体阶段。

用任务 ID、对象/动作 ID、实际作者源和消费者连接职业工作；计划指定必要产物、主责、依赖与完成依据。GDD、场景、配置和专业源文件保持自身主源，管理摘要不复制正文。运行证据、技术检查、专业评审和用户认可分别记录。

## 共享工具定位与命令

源码使用含 tools/workflows 的仓库根；安装后使用 game-preproduction/runtime。先核实路径。工具不存在时仍可做专业工作，明确缺少自动状态/证据功能，不能声称已经运行。

`tools/game_workflow.py task --project <项目> create --spec <任务JSON>` 建立结构化任务；`show --id <ID>` 读取记录与有效状态，`list` 查看项目任务。输入含 id、goal、start_stage、end_stage、objects（id/title）、deliverables，按需附 inputs、constraints、authorization。`objective` 默认为 deliver；明确只研究可行性时可用 evaluate，其否定结论不代表能进入下一阶段。

`update --id <ID> --revision <刚读取的版本> --operation <操作JSON>` 保存有依据的变化。支持准备度 readiness、工作计划 plan、实际工作 step、阶段 review、问题 issue 和 pause/resume/cancel/close。操作只记录真实发生的工作，不执行计划、不编造 run；程序与制作工具另行产生实际文件和运行。

计划步骤含 id、stage、objects、owner、description、depends_on、side_effects；owner 对应实际职业 Skill。已有执行步骤不能直接改定义或删除，修复另建有关联的步骤。开始执行先核对前置状态，完成需实际产物和证据。保存采用版本冲突检测，历史位于原任务目录的 .history。

`tools/record_evidence.py --project <项目> --register <证据请求JSON>` 登记真实文件、来源类型/说明、观察者、对象、结果和依赖版本；`--check <项目相对记录路径>` 检查是否过期。宿主工具/人工制作保留原始结果，不补造命令或退出码。证据登记不会把任务自动改为完成，原件与旧判断保留。

## 出口与恢复

旧 Markdown 任务使用 `task ... migrate --spec <明确任务约定>` 启用编排，必须与原文件同 ID；原文不变，其自然语言“已完成”不会变成已通过。`recover --id <ID>` 读取当前步骤、run/session/job、产物变化和写锁线索，不自动重放工作。

用户改变目标时使用 `amend`，携带 `changes`、`affected_stages`、已有 `authorization` 和理由。被影响阶段的当前评审清空，完整旧修订保留在 .history；移出区间的已执行步骤需显式列入 `retire_steps`。正在执行或受阻且有副作用的步骤，重置为 pending 前必须登记实际恢复证据。

阶段出口需准备度说明、适用检查的真实依据、专业判断及明确结果；必须的用户决定沿用已有授权，不能伪造。技术阶段不能用纯策划文档证明运行。任务到终点时执行 close；未纳入的后续阶段保持范围外，不自动扩展。

变更使依赖过期时，状态读回标明需复核，不能把旧通过摘要继续当当前事实。问题关联受影响对象与阶段，未受影响结论保留。暂停/恢复只更新任务意图，不自动关闭用户编辑器或重放引擎请求；具体执行恢复复用原 run/session。文件锁异常时先检查记录的进程和现场，不盲删锁或重复写入。
