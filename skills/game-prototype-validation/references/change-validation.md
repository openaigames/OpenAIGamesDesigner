# 变更验证与回归

用于新增/修改功能与资产、缺陷修复、机制原型和垂直切片的实际验证。先确定需要证实什么，不能把所有任务都变成“做一个最小原型”。

## 选择验证范围

读取本轮差异、验收要求、受影响消费者、已知问题和可用版本。沿变更路径选择核心流程与直接受影响的边界；外观替换也可能影响碰撞、挂点、UI 命中或性能，按真实依赖检查。

| 目标 | 可用方法与边界 |
| --- | --- |
| 规则/功能正确 | 可复现输入、状态与预期结果，必要时自动测试；一次成功不证明所有边界 |
| 资产集成 | 引用、导入、实际尺寸/朝向、生命周期、真实场景表现；文件存在不证明可用 |
| 缺陷修复 | 原复现步骤及邻近路径；旧版本不能运行时记录证据缺口，不虚构前后对照 |
| 体验假设 | 带任务的试玩与观察，记录参与者条件及提示干预；开发者自评和外部玩家反馈分开 |
| 性能/稳定性 | 明确构建、设备、场景负载、设置、采样方法和指标；不同环境数据不直接当改善证据 |
| 垂直切片 | 代表性流程的玩法、美术、技术集成，以及对应范围的质量与制作可行性；不按全部成品内容验收 |

原型允许明确标识的占位资产；正式视觉验收要对照本轮认可目标。是否需要重新实验取决于旧证据是否仍适用，不因新功能默认废弃全部历史测试。

## 测试卡与执行

沿用现有测试系统；没有时在变更/实验记录中保留：对象与版本、前置条件、步骤/输入、预期或观察问题、实际结果、证据位置和限制。小检查无需单独文件，重复执行或跨人交接才细化。

功能判定标准在执行前明确；探索性体验研究允许得到不确定结论，不为方便验收编造满意度阈值。设计规则确实未知时可以先测试现状，不能把现状自动升级为目标。

执行请求在授权范围内使用可用工具。运行缺失、工具不可用或资源超过已知范围时，交付具体阻塞和可继续的检查，不将计划写成已执行。引擎构建、真实试玩与自动化测试的结论分开。

## 结果与回写

逐项标注通过、失败、未执行、受阻；体验假设另记支持、不支持或证据不足。用户接受风险不改变原始结果，单个测试失败也不自动否定整个项目。

对发现的问题记录复现、影响、证据和建议责任层（规则、配置、资产、导入、实现、环境）；原因未证实写候选。修复后保留原结果，再追加复测记录。失败时依据证据选择修复、调整设计、补测或停止，不无限生成新内容掩盖问题。

结论链接回原功能、假设和相关任务；注明哪些设计判断应调整、哪些资产/实现待改、哪些旧证据需复核。没有权限更新任务或宿主状态时提供交接并说明未同步，不能伪称任务已关闭。

评审里程碑时总结目标流程实际覆盖、未执行部分和已知风险。仅覆盖功能正确时不宣布体验、美术、性能或整款游戏全部通过。原型或切片可以就是最终交付，无需强制扩为完整游戏。
