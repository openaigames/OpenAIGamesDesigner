# 原型、垂直切片与交付的证据评审

在已有任务和里程碑上判断下一步，不由文件数量或命令 passed 自动推进阶段。执行证据读取 [运行记录](run-evidence.md)，体验问题使用 [实验设计](experiment-design.md)，视听与性能分别使用对应专项方法。

## 对照本轮承诺

先确认目标是机制实验、代表性品质、对外试玩还是某范围成品交付，以及对应的工程/构建版本。只要求切片的项目无需被推到完整发售。目标已经明确时直接据此检查，缺少影响判断的验收范围再澄清。

| 维度 | 需要回答的问题 | 适用证据 |
| --- | --- | --- |
| 原型机制 | 关键选择和反馈是否成立，哪些原因仍未区分 | 实验条件、观察、实现正确性和限制 |
| 代表性集成 | 核心流程是否连贯，关键系统和正式表现是否在同一版本工作 | 实际完整路径、场景和运行资源 |
| 品质 | 本轮约定的可读性、操作、视听及性能是否达到目标 | 对应专项检查和目标条件 |
| 制作可行性 | 这种内容能否继续生产，依赖、实际投入和返工是什么 | 代表资产/功能的生产记录，不是纯估算 |
| 交付可用性 | 接收方如何打开、运行和继续编辑 | 构建、可编辑工程、依赖、说明与已知问题 |

各维度可有不同状态。功能路径完成而视觉占位可以满足某个原型，不能自动满足已经承诺正式品质的切片。

## 假设例：切片能运行但代表负载未测

假设约定切片包含一个完整遭遇和六个敌人同屏。现有证据只覆盖两个敌人、开发机编辑器运行以及占位音效。结论应分别写已证实的流程、尚未测的负载/目标包、与约定不符的声音交付；不能因为构建命令成功批准整体验收。

可以提出补测、缩减本轮承诺或限定使用用途的选项，并说明损失与剩余工作。用户接受“内部试玩版”只改变交付用途和风险取舍，原来未测的性能仍是未测，不改写历史结果。

## 形成可接续结果

把缺口变成具体任务：所需输入、实际产物或实验、受影响消费者、完成依据及依赖。优先处理阻止判断主目标的问题，避免把所有未来功能列为切片阻塞。

交付时核对入口、运行/构建方法、所需依赖及可编辑来源；只有实际在另一目录或环境恢复运行过，才报告相应可重建/可恢复结论。源码哈希和压缩包存在不足以证明依赖完整。

在管理入口链接评审、实际版本、已完成与待办、用户取舍和下一动作。保留原始运行记录与失败报告；内容或配置改变后重新判断哪些证据仍适用，不机械重做全部验收。
