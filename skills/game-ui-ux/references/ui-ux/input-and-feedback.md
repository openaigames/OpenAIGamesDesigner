# 焦点、输入与操作反馈

## 明确谁接收输入

检查游戏、HUD、菜单、弹窗及文本输入之间的所有权。打开/关闭或叠加界面时明确焦点进入、保持和返回；恢复到已被删除的控件要有合理后备位置。

键鼠、手柄、触摸按项目支持范围设计，不能假设所有界面都有悬停。导航顺序应符合任务和空间关系；列表刷新或排序后尽量保持可解释的选择，而非跳到意外对象。

输入提示跟随实际绑定与当前设备。长按、双击、拖动和组合输入需要说明开始、进行、取消及提交时点；不要仅以动画进度推断提交成功。

## 操作过程要可分辨

区分选中、按下、请求已接收、处理完成。按键音不证明系统操作成功。异步请求期间如何阻止重复提交、允许退出或保留结果，由实际操作性质决定。

确认只用在误操作代价确实较高且无法合理撤销的场景，普通选项切换不层层弹窗。可撤销操作要说明撤销范围和生效时机，不能承诺工程未支持的恢复。

界面暂停与世界暂停分别说明。打开菜单后游戏仍运行时，角色输入、资源变化和危险反馈要一致；不因为是单机就默认世界必然暂停。

## 失败和反馈

禁用原因应指向可理解的条件；失败后保留可以复用的输入。信息变化后避免显示旧成功状态。提示不能抢占需要持续操作的输入，也不能遮住关键对象。

例：手柄确认打开详情，同一次输入不应透传到详情中的购买按钮。检查输入消费、界面出现时点和返回焦点，不用添加重复确认掩盖原因。

交付焦点与输入约定、状态反馈、重复请求/取消/返回边界，以及代表设备的完整操作路径。实际输入测试与视觉稿检查分开。
