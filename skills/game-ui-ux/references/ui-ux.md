# 游戏 UI/UX 与教学

用于玩家任务、信息结构、界面流程、输入焦点、操作反馈和机制学习。不等于 UI 美术风格，也不意味着创建浏览器看板。

从玩家想完成什么、当前看见什么和哪里受阻开始，使用 [设计推理入口](../../game-design/references/design-reasoning.md)。现有界面局部问题只处理受影响流程，不自动重新设计全部菜单。

| 问题 | 参考 |
| --- | --- |
| 信息组织、流程、选项和结果 | [任务与信息结构](ui-ux/tasks-and-information.md) |
| 焦点、设备、确认取消与状态 | [输入与反馈](ui-ux/input-and-feedback.md) |
| 教学、辅助与实际可用性 | [学习与可用性](ui-ux/learning-and-usability.md) |

规则属于相关系统，UI 呈现条件、接收意图并解释结果；技术负责实际数据和输入接入，美术负责视觉语言与资源。状态要覆盖成功之外的实际情境，不能只交一张漂亮的默认页面。

需要独立交付时用工具包 `templates/feature-spec.md`，细化玩家任务、流程、数据来源、焦点、输入、教学和反馈；实际观察使用 `templates/validation-report.md`。线框、视觉稿、已接入数据和试玩验证分别记录。三维世界提示、声音和控制器反馈也可以承担信息，不强制每个需求变成屏幕面板。

## 制作实例：战斗结束后无法顺畅重试

画出进入—操作—胜/负—重试的完整状态和焦点归属。胜负从游戏权威状态读取，按钮只提交重试意图；重试被拒绝时说明正在加载或其他真实原因。先制作最小可操作界面，接入真实生命值、结果和重试执行记录，再统一排版、对比、过渡和设备提示。

普通输入完成一次流程后，检查手柄/键盘初始焦点、鼠标切换、重复按下、暂停打开菜单、返回战斗和再次失败。若焦点落到隐藏控件，先修焦点生命周期；不让玩家多按一次来掩盖状态错误。若有确认弹窗，取消返回原按钮而不是任意首项。按钮反馈与游戏真正重新加载分别记录。

观察者需记录实际操作路线、停顿/误解和画面或控件状态。自测能证明功能与观察到的可读性，不能代替目标玩家的学习测试；完成声明保留这一区别。公开夹具中的目标 HP、结果提示和重试入口是可检验的工程路径，字体/动效和无障碍目标仍由具体游戏约定。
