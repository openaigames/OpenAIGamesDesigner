# Game Concept.md · 初期结构预设

此结构用于新作概览；已有项目的方向判断和局部修订见 [定位与方向变更](project-fit.md)。无定位变化的功能/资产任务可以不修改概览。

默认按以下顺序，写成面向陌生读者的连贯介绍。篇幅随内容与用户要求调整。候选标候选，已明确内容直接表达，避免每句重复免责声明。

1. 项目介绍：类型、身份、目标、主要行动、核心取舍与吸引力。
2. 设计支柱 / Game Pillars：体验原则及其对设计选择的要求；数量由项目需要决定，候选先讨论。
3. 目标玩家：预期人群与动机，没有调研时标为假设。
4. 独特体验：希望形成的体验或情绪节奏，不写无依据的市场优势。
5. 世界观与玩家身份：能支撑动机的基本情境，具体剧情可留白。
6. 典型游玩体验：一个简短设计示意，串起动机、选择与反馈，不冒充真实试玩。
7. 影响定位的制作策略（适用时）：只概述与核心体验或项目身份有关的制作选择，并链接美术记录。具体资产、来源、许可、版本和交付状态由 Art Direction 或已有权威清单维护；普通素材替换不要求更新概览。

用户只给模糊想法时先提当前关键问题；明确要求先写草案时可以用候选形成可讨论的版本。认可模板不意味着认可其中的示例玩法。

首版范围、不做清单、团队预算工期属于风险与制作边界；详细系统、规则与双循环在 GDD 展开。不要为了看似完整加入具体任务、装备数量、死亡惩罚或剧情设定。

## 概览自检与接续

概览可以短，但读者应能从正文理解玩家的处境、反复做的事、需要取舍的原因、结果反馈和希望形成的体验；“某类型游戏＋若干功能”或复制用户原话不能替代这些关系。有依据的内容直接展开，关键未知说明会影响什么决定，不把未知补成事实。

支柱说明保护的体验及一个支持/冲突的设计选择；未获确认的支柱仍标候选。目标玩家与吸引力来自用户目标还是未经验证的假设要可辨认，不因已经做出原型就声称受众和趣味性成立。只在确有取舍时记录理由，不强编参考游戏、竞品分析或世界设定。

制作过程中先区分用户要求、授权范围内采用的默认方案与已观察到的实现。前两者影响定位时更新正文，第三者用于指出设计差异或链接证据，不能反向伪造“原本的设计意图”。详细规则链接 GDD，当前范围/任务链接管理记录，体验验证链接风险记录；不要把这些表格复制进概览。

交接前用一个已有依据的设计示意检查：从玩家目标到行动、选择、后果是否连贯。如果文档原先只有一句需求，首次形成可玩版本后补足这些已知关系；已有清晰概览且本轮定位无变化时维持原文。
