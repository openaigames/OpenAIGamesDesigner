# 功能规格与设计变更

后续修订沿用既有功能规格，GDD 只汇总当前系统关系与链接。跨方向影响以同一变更记录关联美术、技术和验证的实际改动，分别标注设计、实现、验证状态；回写管理摘要，定位不变无需改概览。依据已明确且在授权范围内时继续完成相关文档修订，不停留在一句“建议同步”。

用于新增系统、修改玩法、内容设计、参数调整或将方向展开为可实现规格。独立调用时直接检查当前功能，不要求先经过管理 Skill。

## 建立当前行为

读取本轮相关的设计、配置、实现与已有测试/试玩记录。分清“现在实际怎样”“文档希望怎样”和“用户要改成怎样”；没有运行过的代码理解标为静态判断。沿用现有文件和命名，没有 GDD 也能交付局部规格。

先确认内容扩展还是规则扩展：增加同类型敌人可能只是配置与资产，新敌人的独特行为才需要规则和接口变更。改数值优先找到有效配置来源、覆盖关系和消费者，避免同时更改数值与机制而无法解释效果。

## 交接规格

使用项目现有格式。没有格式且需要独立规格时，可写在现有 GDD 章节或 `design/features/<功能名称>.md`，由管理记录链接它。按影响选择字段：

可采用工具包 `templates/feature-spec.md`。它提供统一交付骨架，专业参考决定需要展开的内容与深度；不再为每个玩法专题维护另一套模板。

| 内容 | 要能回答的问题 |
| --- | --- |
| 目标与范围 | 哪种玩家行动/选择要改善？本轮保留、增加、修改或移除什么？ |
| 输入与触发 | 谁在什么条件下触发？输入冲突、重复输入、不可用时怎样反馈？ |
| 状态与规则 | 状态如何进入、变化和结束？资源成本、目标选择、成功/失败是什么？ |
| 反馈与信息 | 动画、VFX、声音、UI 分别表达什么事件？玩家怎样判断结果？ |
| 数据与边界 | 参数名称、单位、约束、默认来源；例外、取消、中断、跨场景/跨局行为（适用时） |
| 关系与验收 | 影响哪些已有系统、资产与技术接口？用什么场景确认行为？ |

数值未知可保留候选或设计范围。实施确需数值时根据授权给出明确标注的暂定配置，便于后续调整，不冒充已调优值。规格引用现有数据表而非维护另一份数值真相。

## 按专业问题展开

- 战斗与移动：动作状态、输入缓冲/取消窗口（需要时）、攻击与命中、受击/死亡、镜头与反馈；表现时序与规则时序分清。
- 关卡与遭遇：目标、空间/路线、遭遇节奏、信息与风险回报、进入/退出和失败恢复；以能验证的场景描述代替只列地图名。
- 成长、经济与构筑：资源来源和消耗、选择代价、解锁条件、组合限制、失效/重置规则；检查无成本循环和明显支配策略，不把静态计算称为平衡验证。
- UI/UX：玩家任务、信息层级、界面流、输入焦点与返回、不可用/空/异常状态、手柄和可读性（按平台适用）；布局描述不替代交互规则。
- 叙事与任务：触发条件、分支状态、文本与规则的对应、重复/跳过/中断行为；已有世界约束优先，不为新机制任意改设定。

只加载本轮涉及的专业问题，不要求所有功能覆盖上述类型。

## 增量修订

明确旧规则与新规则的差异，指出对既有内容、配置、存档、教学和测试的影响。用户已选定方向时直接展开；只有会迫使擅定关键体验时才提问。

提交策划交付时列出需要美术表达的事件、需要技术实现的状态/数据和需要验证的判断。跨专业影响是交接请求，不意味着其他专业已经修改或通过。用户要求实际实现时继续使用可用工程工具；工具不可用则准确标记停在规格/准备阶段。

替换或删除规则时检查引用它的敌人、道具、关卡和旧数据；不存在的系统写不适用。小修订只更新相关内容，保留已有人工修改和决定历史。
