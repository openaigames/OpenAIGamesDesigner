# 战斗系统设计：入口与使用方法

这是指导模型设计、审查和修订战斗系统的方法，不是某款游戏的战斗方案。实际规则写入该项目的 Combat Design.md、GDD 或已有规格。本参考不预设动作/射击/回合制、镜头、题材、引擎、联网或成长系统。

只在本轮需要对抗、攻击/防御、受击或敌人应对方法时使用。它不负责给整款游戏分类。先按 [设计推理入口](design-reasoning.md) 理解实际需求；跨活动的关系使用 [共享方法](shared/experience-and-systems.md)，瞄准/发射的深入问题使用 [射击参考](shooting-design.md)。射击没有对抗或伤害时不必加载 Combat；探索也无需先通过战斗设计。

## 先判断本轮设计深度

| 请求与现状 | 工作重点 | 不应替代成什么 |
| --- | --- | --- |
| 从零建立战斗系统 | 体验目标、玩家决策、核心关系与必要子系统 | 罗列招式或擅定完整功能清单 |
| 已有系统增加能力/敌人/武器 | 建立现有规则，分析新内容改变哪些选择与关系 | 重新立项或重写全部战斗 |
| 制作一个动作/技能 | 在系统约束下完成行为、时序、交互与边界 | 只有动画或技能字段 |
| 调数值、节奏或修复体验 | 区分设计、实现、信息表达与场景问题 | 未查依据就改一批参数 |
| 只研究或讨论方向 | 证据、候选方案、关键取舍 | 未经请求创建工程或宣布验证通过 |

沿用 [功能规格与设计变更](feature-design.md)。从当前需求、已有设计、实际配置及实现读取必要上下文；陌生项目中的未知不能从另一款游戏或演示样例继承。缺少会改变本轮方向的信息才澄清，已有决定直接沿用。资料缺失时可按授权提出清楚标注的候选或暂定规则，不能把所有缺口都变成一串问卷。

不要一次加载七份参考；先读与本轮问题有关的部分，遇到实际依赖再展开。新系统通常从 foundations 开始，局部改动直接进入对应专题。

## 系统设计的最低解释力

完整设计要说明：玩家获得什么信息、面临哪些有意义的选择、承担什么代价、行动怎样改变局面、对手或场景如何回应，以及下一次选择如何产生。机制清单、状态机或伤害公式各自只能说明一部分。

系统之间用关系说明或小型图表达条件、消耗、反馈和约束；再展开需要实现的动作/敌人规格。每个重要机制关联其体验作用与取舍。若一种行为在所有相关情境都更优，检查这是否符合目标，不为追求表面复杂度机械削弱它。

区分整体系统设计和本轮实验范围：完整方向可包含后续内容，原型只选能回答关键问题的因果链，不能将完整产品规格改写成只有木桩和一个技能。反过来，小修订也不需要完成整套系统设计。

## 交付深度与交接

- **方向阶段**：可讨论的体验、决策关系、关键选择和待验证假设；未知可以保留，不预填全部数值。
- **可实施规格**：在本轮范围内消除会迫使实现者擅定规则的歧义，给出触发、结果、关系、边界和可检查的预期。
- **迭代结果**：关联原规则、实际改动、配置版本、观察和下一步；文档或静态计算不能冒充试玩结论。

工程中生效的配置保留一个权威来源。设计阶段可保存候选值与公式；落实到工程后记录来源、版本、单位和理由，导出的只读快照须标明版本，不能维护另一份脱节的参数表。

将表现事件与可读性要求交给美术，将状态/接口/判定与配置要求交给技术，将待证实问题和可复现操作交给验证。GAS 是技术实现选择，不是战斗设计必需项。通用制作阶段继续使用原型、切片或功能变更 workflow。

已有项目格式优先；需要新文件时，系统或动作使用工具包 `templates/feature-spec.md`，实际检查使用 `templates/validation-report.md`。按本入口的七组专题细化规则，不因通用模板省掉动作时序或系统关系。安装包模板由管理 Skill 的 runtime 提供；没有模板时直接维护现有文档。专题是按需分析工具，模板是输出辅助，都不是必须逐项填满的问卷。
