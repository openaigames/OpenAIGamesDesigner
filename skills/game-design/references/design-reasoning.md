# 从创意与现状识别设计问题

这是 game-design 的思考入口，不是要求用户填写的问卷。专业参考的目录服务知识检索，不能成为游戏必须归属的类型体系。项目可采用自己的概念、系统名和组织方式。

## 先理解，再选择参考

从已有上下文识别用户要创造的体验或改变的行为，描述玩家实际行动、可用信息、选择与后果。区分用户明确的规则、参考的具体方面、模型候选、当前实现和未知。局部任务直接从现有规则切入，不能每次重做定位。

检查不同活动如何影响彼此：结果改变了什么信息、条件、关系、资源或目标？连接可以是资源流，也可以是知识、身份、人物态度、世界状态或操作能力。没有联系时先判断它们是有意的节奏变化还是尚未解决的设计缺口，不强迫所有内容服务同一个货币循环。

缺少会改变本轮动作的信息才问关键问题；已有明确授权和输入则推进。用户要求候选方案时可提出互相有取舍的方案，不将建议标为已选。用户拒绝的机制不能因为参考资料出现而重新加入。

## 按问题检索，而非按类型套用

| 本轮问题 | 按需读取 |
| --- | --- |
| 行动为何继续、不同活动如何互相影响 | [体验与系统关系](shared/experience-and-systems.md) |
| 玩家知道什么、为什么愿意承担不确定性 | [信息、选择与风险](shared/information-and-risk.md) |

| 区域空间、路线、段落编排、检查点和灰盒 | [关卡设计](level-design.md) |

这些只是当前可用参考。遇到库中没有的机制，用 [功能规格方法](feature-design.md) 从实际目标构造规则、关系、边界与观察依据；必要时研究相关材料，不将陌生机制硬归类。不要根据“射击”加载全部战斗，不根据“冒险”加入任务、敌人、血条或开放世界。

一个混合玩法要同时分析局部活动与连接。例如“探索带回发现，改变店里与居民的互动”可以先讨论发现怎样改变信息和关系，不擅自补出捕鱼、寿司、员工、稀有度或装备经济。参考作品的标签不能代替这个分析。

## 将推理落实为交付

输出采用该项目自己的语言，记录本轮目标、当前行为、候选/决定、规则关系、必要局部规格、依赖和验证问题。只有材料变复杂才拆文件；不在游戏工程内复制参考库的目录树。

单一明确修改可直接更新相关规格；整体系统设计要解释玩家决策与系统关系；原型只缩小当前实验范围，不抹去整体目标。跨系统关系复杂时可用工具包 `templates/feature-spec.md` 的系统关系部分，也可在 GDD 中简述，无需固定文档数量。

实现和阶段推进复用通用 workflows，专业 Skill 接受实际交接。方案研究不冒充实现；调用了参考不表示已经验证，文件齐全也不能批准阶段。
