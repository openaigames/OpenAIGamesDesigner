# 状态、恢复与灰盒验证

## 定义恢复边界

检查点记录什么由项目规则决定：角色位置、能力/资源、敌人、门、可破坏物、任务和已发现信息是否恢复，需要各自明确。没有死亡或存档机制的项目只处理实际存在的返回/重试规则。

分别考虑首次进入、完成后重访、失败恢复、退出重进以及已有存档载入。进入动画或对话可以重播，但不能因此重复发奖励或锁住路线。互相关联的状态应有共同版本或可解释的恢复次序。

软锁检查针对“玩家仍可操作但无法推进或恢复”的具体路径。不得为了省事强制关闭用户允许的自由顺序；优先明确状态兼容、替代通路或合理恢复。

## 灰盒要保留实验需要的东西

选择能回答问题的区域和起始状态。验证跳跃可达需要真实角色控制和碰撞；验证导航需要足够的镜头、地标和遮挡；验证最终美术可读性则不能只用色块。

记录与正式方案不同的占位内容及其对结论的影响。几何能走通仅支持可达性，不证明玩家知道往哪里走。使用开发者自由飞行或作弊能力的路线不作为正常玩家证据。

## 修改影响与回归

空间变更追踪连接、移动参数、碰撞、导航、交互点、相机、触发器和表现消费者中的实际受影响项。删除一个平台可能同时改变路径与视线，不能只复测最近的一次跳跃。

选择代表状态复测：正常路线、允许的另一顺序、失败重试、返回，以及本次修复的复现条件。多人、生成地图或存档迁移只有项目实际支持时才纳入。

交付区域/场景版本、起始条件、路线与输入、预期/实际、截图或运行记录和未覆盖限制。验收方法与 game-prototype-validation 的可用性/运行证据参考衔接；技能不可用时直接保留这些事实，不猜安装路径。
